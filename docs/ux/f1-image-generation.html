Why this is a decision

SPEC 9 fixes the mechanics: the active model lives in the database and is switchable without a deploy, the seeded default prunaai/p-image returns one image per request, and black-forest-labs/flux-schnell only turns on where a batch of up to four variants is wanted, such as choosing a portrait. It does not fix any of the three things a GM actually clicks through: where "generate" lives, what happens by default when they click it, and how the per-entry or universe-wide style gets edited. Picked by accident, this becomes either a settings page nobody finds, or a button that quietly spends four generations every time because nobody built the single-image path a level up in the same flow.

Guardrail 6 images are born private to the GM and never flow automatically into the players' wiki, even once accepted onto an entry (#71). Whatever surface starts generation has to make that boundary visible, not just true in the database.

Options

A

Generate from the entry, toggle for variants

A button in the entry toolbar opens an inline panel. Default is one image; a second action switches the model and the layout.

Buys

  • One button, discoverable exactly where a GM is already looking at the entry.
  • Default matches the seeded model: cheap, fast, one image for the common case (a place, an item, an event).
  • Style stays editable inline, no trip to a settings page to see what it is.

Costs

  • Two rendered states to design and keep in sync: a single insert and a pick-one-of-four grid.
  • The variant toggle only earns its keep if a GM actually notices it exists; nothing here surfaces it before the first click.
  • A per-entry style override is invisible to anyone else looking at the universe's overall look.
B

Type decides, no toggle

Character entries always get four variants to pick from, everything else gets one image with no picker. No manual choice anywhere.

Buys

  • Matches SPEC 9's own example exactly: batches "such as choosing a portrait".
  • Zero decisions for the GM. Nothing to explain, nothing to miss.
  • No code path branches on user choice, only on entity type.

Costs

  • A GM generating a place who wants two options to pick from has no way to ask.
  • The rule lives in entity type, so reclassifying an entry silently changes what "Generate" does next time.
  • Four generations fire for every character by default, background NPCs included; the exact spend F2's warm budget worries about.
C

One action, always confirm the spend

"Generate image" always opens a choice: one image or four, cost shown for each, before anything runs.

Buys

  • Never surprises anyone about spend; the same principle F2 needs for imports.
  • One code path instead of two: the dialog, not the entity type, decides the model.
  • Discoverable by construction: the choice is in front of every GM, every time.

Costs

  • One extra click on the common single-image case, every single time.
  • A dialog people click through without reading defeats its own purpose; the risk is silent if it happens.
  • Needs the per-credit cost numbers kept current in the UI, one more place F2's pricing has to stay in sync.

Rejected outright

Insert straight into the entry and let a "visible to players" toggle catch it later

Generating an image and dropping it directly into the entry body, trusting a later reveal step to keep it from players, is the same shape as auto-applying an AI edit: it skips the moment a human looks at that specific output and says yes. Guardrail 6 is explicit that images are born private and never flow automatically to the players' wiki; "later" is exactly the word that guardrail exists to remove. Every option above keeps insertion a separate, visible step from generation.

What I would take

C, defaulting the radio from entity type

Take C. Image generation is the single most expensive per-click action in the product; four credits against one, a straight 4x; and it is also the one place a GM is most likely to click twice without thinking, the way anyone re-rolls a portrait they don't love. That is exactly where a silent default is riskiest and an explicit, fast confirm costs the least: one extra click on a screen the GM is already dedicating to "make a picture", not one they are passing through on the way to something else. Pre-select whatever option B would have chosen automatically, so the common case is still one click plus Generate.

Cheapest way to find out this is wrong: log which radio ships selected versus which one gets clicked. If GMs consistently flip the default, the dialog is friction with no information content and the product should collapse to B. If they leave it alone, the dialog earned its place.

What this locks in

  • #66 the generate entry point ships as a dialog with both models named and priced, not a single hidden button.
  • #71 generation and insertion stay two steps everywhere, so the players' wiki filter (revelation-driven, SPEC 10) never has to special-case a freshly generated image.
  • #65 the "Generated" badge is the violet AI-marking chip from C1, placed on the image itself, not just in the entry's kicker; it has to survive being cropped into a portrait thumbnail elsewhere in the app.
  • Deferred: a full universe-level style manager with history of past prompt_modifier values. The inline edit chip covers "change it now"; a browsable style history is a separate settings-surface decision, not this one.
