Why this is a decision

SPEC 6.6 names seven playbooks and a generic fallback, and says the import must produce a useful proposal within minutes because the competitor is Obsidian, which asks for nothing on day one. What the spec does not say is how the GM tells Canonry which world they are handing over. That single screen sets the tone for the whole pipeline: get it wrong and either the wrong playbook runs on a vault it cannot read well, or the GM spends their first minute filling in a form before anything happens at all.

Guardrail 5 whichever option wins, a GM on a free World Anvil tier has to be told plainly, before they upload anything, that there is no clean door in for them. SPEC 6.8 accepts that gap rather than solving it. A screen that stays silent about it turns an accepted limitation into a support ticket three days later.

Options

A

One dropzone, source detected

A single drop target for anything. Canonry opens the archive, guesses the source from its shape, and says what it found. No source picker at all, closest to what Obsidian itself asks for on day one.

Buys

  • Zero questions before the first useful signal, matching Obsidian's own bar.
  • One code path decides the playbook, so there is nowhere for the GM's choice and the detector's guess to disagree.
  • The generic case looks like a legitimate outcome, not an error screen.

Costs

  • A wrong guess (a Kanka export that also happens to be a folder of JSON) runs the wrong playbook with no checkpoint to catch it.
  • The World Anvil free-tier gap has nowhere natural to live, since there is no moment where the GM says "World Anvil".
  • "Pick manually" is a rescue path bolted onto the happy path, easy to under-build.
B

Source chosen first

Seven playbook tiles plus generic, picked before any upload. The dropzone that follows is scoped to that source and its export instructions.

Buys

  • The World Anvil gap is said at the one moment it is relevant, before anyone uploads anything.
  • Upload instructions can be specific ("export the vault as a zip") instead of generic advice.
  • No detector to get wrong; the GM's word is authoritative.

Costs

  • One extra click and one extra decision before the first upload, exactly the friction Obsidian does not have.
  • A GM who does not know their own export format (a OneNote user unsure if it is a PDF or a .onepkg) is stuck choosing blind.
  • Seven tiles plus generic is a wall of unfamiliar words for a first-time visitor.
C

Detect, then confirm

One dropzone like A, but the detected playbook is a proposal with an editable field, not an instruction that runs immediately.

Buys

  • The GM always sees which playbook is about to run and why, before it runs.
  • A wrong guess costs one click in a dropdown, not a wasted import.
  • The World Anvil gap can be shown the moment someone changes the dropdown to World Anvil, same message as B.

Costs

  • One extra screen and one extra click versus A, on the exact metric SPEC 6.6 measures in minutes.
  • For the 90% case where detection is right, the confirm step is pure overhead most GMs will not read carefully.
  • Two things can now disagree (the detector's guess and the dropdown's value), which is one more state to test.

Rejected outright

A "Connect your account" button for World Anvil or Kanka

It looks like the obvious way to remove the free-tier friction, and it is exactly what SPEC 6.6 and 6.8 close the door on: "there is not a single API integration in this list, and that is the point." Kanka's terms restrict commercial use of their API on a customer's behalf (SPEC 6.9), and World Anvil's API needs a Guild subscription and a fifteen-day human review, so a connect button would still fail for exactly the GMs it is meant to help. It also reintroduces an Entra-ID-style consent screen and a stored delegated token, which is a second thing sitting between the GM's content and Canonry. Guardrail 5 promises data transparency in plain words; a live OAuth grant to a third party is one more provider in that sentence, for a door that stays shut for the free-tier users it targets.

What I would take

C, detect then confirm

I would take C. It keeps the single dropzone that competes with Obsidian's zero setup, and it spends exactly one extra click to close the two real risks in A: a wrong guess that runs silently, and nowhere to put the World Anvil free-tier message before the job starts. B's tile grid is the right idea for the World Anvil case specifically, but it makes every GM pay a decision upfront for a problem only some of them have.

Cheapest way to find out this is wrong: ship C, then log how often the dropdown gets changed away from the detected value. If it is almost never touched, the confirm step is theatre and A is the better default with a manual override kept for the rare miss. If it is touched often, C earned its extra click.

What this locks in

  • #41 the Obsidian playbook has to expose enough detection signal (the .obsidian folder, wikilink density) for the confirm card to say something more specific than "zip file uploaded".
  • #43 the World Anvil playbook only ever sees a Full World Export zip, since the free-tier message in the mocks above sends everyone else to the generic path before a job is ever created.
  • #44 the generic playbook has to produce a genuinely useful first pass, because C makes "generic" a visible, named outcome rather than a silent fallback, and a bad generic result now reads as a product failure instead of an edge case nobody saw.
  • Hard to undo: once GMs learn the dropzone always leads with detection, a later switch to source-first (B) would feel like new friction, not a simplification.
  • Deferred on purpose: the estimate and the consent to spend money and quota, which is D2; what the plan looks like once the job finishes, which is D3.
