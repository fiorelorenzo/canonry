Why this is a decision

Spec 5.1 step 3 requires a plan the GM can read and edit before any diff exists: "this change touches four entries, here is why," with entries droppable before generation. That drop is not only about attention, it is the one point in the whole loop where the GM controls cost before it is spent; the premium model writes every diff that survives the plan, the cheap model only ranked candidates for it. Skip or bury this step and the copilot starts writing prose nobody asked to see.

Guardrail 1 propose, never apply, per entry. The plan is where that guardrail starts, one step before the diff: the GM's first lever is not accept or reject, it is "generate a diff for this at all."

Options

All three below hold the same seven fixture candidates from editing Aldric Vane, ordered by relevance, inside the cap of ten. Uncheck a row to drop it from the plan; the count and the cost estimate at the bottom update live, and a dropped row never reaches a diff.

A

Flat checklist

One list, ranked. Each row: entry, a one-line reason, a cost estimate for the diff it would generate.

Buys

  • One glance ranks all seven; the GM never has to decide which of three groups to open first.
  • Scales cleanly from one candidate to the ten-item cap without a layout change.
  • The relevance order the cheap model produced stays visible, not hidden behind a grouping choice.

Costs

  • Near the cap, a flat list gives no help telling a strong relation-sourced row apart from a weak retrieval one at a glance.
  • Seven one-line reasons in a row read as similar in weight even when they are not.
  • No structure to fall back on if the GM wants "just show me the mentions" during a big propagation.
B

Grouped by reason

The same seven rows, sectioned by how the candidate was found: relation, mention, embedding. Relevance order is kept inside each group.

Buys

  • Near the cap, dropping "everything from mentions" or keeping "everything from relations" is a one-glance decision.
  • Makes the retrieval channel legible, which is otherwise an implementation detail the GM has no reason to know exists.
  • An empty group still renders, so a quiet run does not look like a taxonomy that quietly stopped existing.

Costs

  • Three headers before the first row costs vertical space a seven-item plan does not need to spend.
  • Relevance order across the whole plan is only implicit now; the strongest mention can rank below the weakest relation and the grouping hides that.
  • A GM who does not know what "embedding" means gets a label with no explanation on the plan itself.
C

Small graph with the path

A compact node graph from Aldric Vane outward, one path per relation-sourced candidate. The checklist below still does the dropping.

Buys

  • Shows exactly what "graph neighbours within 2 hops" means instead of stating it as a sentence the GM has to trust.
  • Mother Sennah's two-hop path is the clearest possible answer to "why is she in here at all."
  • Doubles as a sanity check on the graph itself: a captain who commands a faction that protects a tavern keeper is a path worth seeing.

Costs

  • Explains four of seven candidates and needs the plain list anyway for the other three, so it is additive weight, not a replacement.
  • A real ten-entry plan with several two-hop paths gets visually busy fast; this fixture is close to the best case for the graph, not the worst.
  • Needs its own layout engine and interaction model that the other two options get for free from the shared row kit.

Rejected outright

Generate every diff first, let the GM delete what they do not want after

Tempting because it removes a step: no separate plan screen, just a reviewed set the GM can prune. It burns the premium model's writes on entries nobody asked to see, which is the cost problem this decision exists to prevent, and it relocates Guardrail 1's accept-all pressure rather than avoiding it: facing ten pre-written diffs nudges toward skimming and reject-all instead of a real per-entry choice made before any of them existed.

What I would take

A, flat checklist

Take A. For the size this plan actually runs at (capped at ten, and the fixture run is seven) a flat ranked list says everything B's headers say, just without paying for them every time. B earns its keep only near the cap, when the GM is genuinely choosing between "keep everything from relations" and "cut the mentions," and that is a real but occasional case, not the common one. C is the most honest answer to "here is why" for the entries it can draw, but it explains at most half the list and still needs A underneath it, so it is additive complexity for a fixture-favourable four of seven, not a replacement for the checklist anyone will use every time.

Cheapest way to find out this is wrong: instrument what GMs actually uncheck. If drops cluster by reason type (always the mentions, never the relations) rather than by individual candidate, that is the signal to promote B's grouping from "not chosen" to "the real answer once volume grows," without having shipped it speculatively first.

What this locks in

  • #50 the plan is editable before generation, not just readable; a dropped row must be excluded from the diff-generation call, not merely hidden in the UI after the fact.
  • #49 candidates carry their source (relation with hop count, or retrieval reason) as data, not just as plan copy, since B's grouping and C's paths both read directly off it.
  • Hard to undo: the cost estimate trains the GM to treat dropping entries as a spend decision. Removing the estimate later would remove a reason to use the plan at all.
  • Deferred on purpose: whether the plan supports a "select none, then pick" mode for very large runs. Not needed at a cap of ten; revisit only if the cap itself changes.
