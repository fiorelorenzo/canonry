Why this is a decision

The Obsidian vault a GM imports arrives full of [[wikilinks]] (SPEC 6.6): every one of them is a candidate relation, so whatever the editor stores has to read that syntax on the way in even if it renders something else on the way out. What the editor stores also has to round-trip: SPEC 13 ships markdown export from day one as the answer to lock-in, so a rich proprietary document format that only serialises to markdown on the way out is a one-way door dressed as an editor. And the mention itself is not typing a link; it is proposing a relation, sometimes to an entity that does not exist yet, which is meant to be the cheapest way canon grows rather than a typo the GM has to notice and fix.

Guardrail 1 a mention becoming a relation is a canon write. It goes through propose and accept like every other AI-touched change, even when "the AI" here is just pattern-matching a bracket against the alias table.

Options

A

Markdown source

A plain textarea. What you type is what is stored, character for character; syntax stays visible as literal characters throughout.

Buys

  • Exactly what is stored is exactly what is on screen; nothing to trust about a hidden conversion.
  • Perfect, lossless round-trip to markdown export by construction.
  • Zero surprise for anyone arriving from Obsidian's own source mode.

Costs

  • Reads like code even to someone who never asked for a code editor.
  • Bold, headings and mentions are all just brackets and asterisks until you squint.
  • The one thing SPEC 4.2 wants to feel automatic, typing a mention, looks identical to typing a bug.
B

Rich text surface

A WYSIWYG contentEditable. No markdown characters ever appear; formatting comes from a toolbar or its shortcuts, mentions render as chips from the first keystroke.

Buys

  • Closest to Google Docs, which SPEC 2 names as the other thing GMs already use instead of a wiki tool.
  • A mention chip looks exactly like the finished relation it represents, no punctuation to parse.
  • Nothing to teach about syntax at all; the toolbar is the whole manual.

Costs

  • The canonical stored form becomes a rich document, not text, so markdown export (SPEC 13, #21) is a conversion, not a serialisation.
  • Re-importing raw Obsidian wikilinks means silently up-converting them into the rich format on the way in, invisibly.
  • Pasting a paragraph from an existing markdown note has to be interpreted rather than simply accepted.
C

Markdown with live decorations

Type markdown, see it decorated as you type: bold text renders bold while the asterisks are still there to edit, a resolved mention becomes a chip, an unresolved one gets a dashed underline instead of disappearing into brackets.

Buys

  • Markdown text is still the stored form, so export round-trips exactly like option A.
  • Reads close to finished prose while writing, without hiding what will end up in the file.
  • Matches Obsidian's own default editing mode, live preview, which most imported GMs already know.

Costs

  • Genuinely harder to build: decorations have to track cursor position without eating keystrokes.
  • An unresolved mention has to stay visually distinct from a resolved one without becoming noise.
  • Copy-paste from elsewhere can carry formatting the decorator has to normalise rather than trust.

Rejected outright

Auto-creating the relation the moment a mention resolves

The moment a typed name matches an alias, silently writing the relation row feels like the editor doing its job. It is Guardrail 1 broken twice over: a relation is a canon write, proposed and accepted like any other, and if the name does not resolve at all the tempting shortcut is worse, quietly creating the entity too. SPEC 4.4 already names the right shape for that second case, a proposal of kind draft_entity: a stub appears in Proposals, evidence attached, waiting to be accepted, exactly like everything else the Loremaster suggests.

What I would take

C, with [[ and @ both opening the same menu

Take C. It is the only option where the stored form is genuinely markdown, so export (#21) is a serialiser rather than a translator, and it is also the only one that looks like writing rather than either code or a word processor. It happens to match Obsidian's own live preview mode, which is not a coincidence worth ignoring: SPEC 2 names Obsidian as the actual competitor, and most of the first users arrive having already trained their hands on exactly this editing metaphor.

On mention syntax specifically: trigger the same autocomplete menu on both [[, because that is what an imported vault is full of, and @, because that is the muscle memory everyone else brings from Slack, Notion and Linear. Both resolve through the same menu shown above, and on save both normalise to one canonical stored form, [[Canonical Name]], so the file on disk never has to represent two ways of saying the same relation.

Cheapest way to find out this is wrong: build the decorator against a paragraph pasted straight from an exported Obsidian note, not hand-typed fixture text, and see whether block references, embeds and Dataview inline fields (SPEC 6.6) survive the round trip undecorated rather than mangled. If they do not, that is a decorator bug to fix, not a reason to fall back to option A.

What this locks in

  • #105 this page is that ticket's own design: the editor surface, the trigger characters and the one-click confirm on a mention become its acceptance criteria directly, not an interpretation of them.
  • #15 autocomplete is a query against the entity table's aliases[] column; if aliases are not cheaply queryable, every keystroke in the menu degrades into a full-text search instead of a lookup.
  • #21 whatever this page decides the editor stores as its source of truth is exactly what #21 has to walk back into a file; choosing option B here would have turned that ticket into a lossy converter instead of a re-serialiser.
  • Deferred on purpose: the visual language of a confirmed relation chip versus an unresolved one in the shipped product belongs to C1. The propose/accept screen a draft_entity lands on belongs to C2 and C6, not to the editor itself.
