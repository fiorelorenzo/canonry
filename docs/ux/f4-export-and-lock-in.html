Why this is a decision

SPEC 13 already decided that markdown export ships day one, because it costs little and answers the lock-in objection Realm Works burned into this community's memory. It does not decide what the export actually contains, where the button lives, or whether the product says so out loud before anyone has signed up. Get the contents wrong and the reassurance is hollow: a zip of files that only render correctly inside Canonry is not really an exit. Get the placement wrong and the feature exists but never does its job, because the GM it would have convinced never saw it before deciding not to trust the product.

SPEC 13 "Markdown export ships from day one, because it costs little and it is the answer to the lock-in objection Realm Works burned into this community's memory."

Decided

A, flat zip export in Settings, unadvertised

Lorenzo took A. That settles the shape: a flat zip, one file per entry, sitting under Settings, with no banner, badge or onboarding step pointing at it. It leaves the marketing half of the question open on purpose, because SPEC 13 ships export on day one specifically to answer the Realm Works lock-in objection, and a feature nobody knows exists answers nobody. Where and how loudly the product says "you can leave" was split out as G10, and has since been answered: one sentence below the landing demo plus a docs page, so the export stops being a secret without the landing page growing a feature list. Decided A rather than the C recommended below, because SPEC 13's promise only holds if the export exists and works from day one, and A ships that without also committing to how the product talks about it.

Options

A

Flat zip, in Settings, unadvertised

One .md file per entry with frontmatter and wikilinks, an images folder, all flat in one zip. Only reachable from Settings → Data.

Buys

  • Cheapest to build: one endpoint, one zip, no folder logic.
  • Wikilinks work unmodified the moment the zip lands in an Obsidian vault, which is the competitor this whole product measures itself against.
  • Nothing on the landing page implies "you might want to leave", which some would argue keeps the pitch clean.

Costs

  • Buried in settings, the feature does not do its actual job: reducing lock-in fear has to happen before signup, not after being asked to go find it.
  • A flat zip of markdown is one manual step short of "own your data", it is not yet a folder a GM can just git init.
  • No visible answer anywhere a skeptical GM evaluating the product would look.
B

Git-ready folder, advertised on landing

Same per-entry files, organised into typed folders with a README and a .gitignore, ready to commit. A section on the landing page shows the tree.

Buys

  • Answers the Realm Works objection where it can change a buying decision: on the landing page, before signup, not after.
  • Git-ready is the strongest form of "not locked in"; diffable, versioned, just like the rest of a GM's notes.
  • Typed folders read naturally in Obsidian's own folder-based navigation too.

Costs

  • Promising this on the landing page before it exists raises the cost of ever
  • Promising this on the landing page before it exists raises the cost of ever changing the format later: it becomes a permanent, public contract.
  • More to build for day one than a flat zip: folder layout, relations resolved into relative links, a generated README.
  • A prominent pre-signup claim needs to work with zero setup, so a visitor without a universe still needs something real to look at.
C

Per-entry button, full zip in settings

Every entry gets an "Export .md" action in its own toolbar. The whole universe exports as a zip from Settings. One sentence on the landing page.

Buys

  • Makes the format tangible at zero cost, the first time anyone is curious.
  • Matches the granularity GMs already think in: one entry, one note.
  • A modest landing-page claim ("export any entry, or your whole world, as markdown") is cheap to keep true.

Costs

  • Two export code paths to build and keep consistent: one entry, and the whole universe.
  • The full zip still has to be built for the case that actually answers the lock-in fear: this does not remove that work, only defers the landing page's attention from it.
  • Git-readiness deferred entirely, so the objection is only half answered on day one.

Rejected outright

Bake unaccepted proposals into the exported files

Mixing pending proposal rows into an entry's exported markdown, so the file the GM downloads (and might commit to git) contains AI text nobody has accepted, is the same failure as auto-applying that edit inside the app, just laundered through a different button. Guardrail 1 requires an explicit accept per entry; an export must only ever contain what is already canon: the human and ai_accepted revisions: never an open proposal.

What I would take

C, with B's folder layout for the full export

Take C for the entry point, a per-entry button is the fastest way to prove the feature is real, and it is nearly free to build first. But give the "Export everything" zip B's typed-folder, git-ready layout from the start, not the flat structure of A: the folder layout is what actually kills the Realm Works fear, and building it twice (flat, then restructured) costs more than building it right once. The landing page gets one honest sentence now: "export any entry, or your whole world, as plain markdown, ready for git"; and earns the fuller diagram from B once the export has been used for real, not promised.

Cheapest way to find out this is wrong: ship the per-entry button first and watch whether anyone ever clicks "Export everything" before the diagram exists. If nobody does, the landing-page real estate B wants is not worth building yet; if people hunt for it, promote it immediately.

What this locks in

  • #21 export ships as typed folders with resolved relative wikilinks and a README, not a flat dump, even though the entry point is the small per-entry button.
  • Hard to undo later: once GMs check a real export into git, the frontmatter field names (id, type, aliases, relations) become a public contract. Renaming a field is a breaking change for everyone who has already committed one.
  • Deferred: whether an exported vault can be re-imported through the generic playbook (SPEC 6.2) is not decided here: export and import are not assumed to be symmetric.
  • Deferred: the full landing-page diagram from B waits on real usage, per the recommendation above.
