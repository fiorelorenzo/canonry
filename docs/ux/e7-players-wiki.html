Why this is a decision

§10 fixes the filter: read-only, a join on revelation, zero configuration from the GM. It does not fix what the reader sees. Two separate questions hide inside the register's one line. First, does this surface wear the app's own chrome, or does it look like nothing else in the product? Second, and the one with real teeth: when a name has been spoken at the table but its entry has no revealed content of its own yet, what happens when a player follows that name?

The skin question resolves quickly once stated plainly: the players' wiki is public, read by people who have never seen the GM tool and never will, shared as a link. It is closer to a fan wiki than to an editor, so it gets its own light, warm, book-like skin; no sidebar, no Ask button, no proposal count. The GM view below is the same Ashen Ledger entry rendered in the app's own working chrome, for contrast.

Guardrail 6 nothing unreviewed is ever published to players. The right pane's secret and GM note exist server-side; the left pane's API response never contains them at all; not styled invisible, genuinely absent. That is what #85 tests.

Options

A

Hidden entirely

Nothing undiscovered exists in the players' wiki. No listing, no search hit, and a mention of an unrevealed entity renders as plain text, not a link.

Buys

  • Zero spoiler surface: a name the GM has not built out yet cannot be found by browsing.
  • Simplest possible rule to reason about: revealed shows, unrevealed does not exist.
  • An index or search page never has to explain a result that leads nowhere.

Costs

  • Inconsistent reading experience: some phrases are links, some look identical but are not, for no visible reason.
  • A curious player cannot bookmark "the Ashen Ledger" to revisit once more comes out; it is a dead end every time.
  • Feels like a bug on a first read, not a deliberate design, since nothing explains the missing link.
B

Listed as a name, nothing behind it

The mention renders as a normal link. Following it before the entry has its own revealed content lands on a plain, generic empty state.

Buys

  • Every mention in revealed prose stays a real, working link; the reading experience is uniform.
  • Cheapest of the three to build: one generic empty-state template, reused everywhere.
  • Matches how broken or thin pages already look on most wikis, so it needs no new explanation.

Costs

  • Reads as broken, because it is indistinguishable from an actual bug or a deleted page.
  • No signal for "come back later"; a player has no reason to ever revisit this link.
  • Says nothing about type or relevance, so "The Ashen Ledger" and a genuine 404 look identical.
C

Shown as a gap

The same link, landing on a page that names the gap honestly: type known, content not, framed as something the party has not filled in yet.

Buys

  • Honest about exactly what "if it came up at the table it shows up" already implies: the name is out, the rest is not.
  • Gives players a natural bookmark; the page fills in on its own as later sessions reveal more.
  • Reads as a feature (a mystery board) rather than a defect, which a generic empty state cannot claim.

Costs

  • The type badge ("faction") is itself a small piece of information a GM might not want confirmed yet.
  • Needs its own copy and template, not a reused generic empty state; a real component to design and maintain.
  • "Not yet discovered" on a page a player reaches by search, rather than by a revealed mention, still confirms the name exists at all.

Rejected outright

Send the real content and hide it with CSS

Render the whole entry, secrets included, and blur or collapse the unrevealed parts client-side so the page "looks right" while still being one stylesheet away from the truth. It is tempting because it reuses the exact same rendered entry as the GM view with no server-side branching. It fails outright: blurred text is still in the DOM, readable via view-source, a screen reader, or a browser's own dev tools, by any player mildly curious about why a paragraph looks smudged. Guardrail 6 nothing unreviewed is ever published to players; sent and styled invisible is still sent. This is exactly the failure #85's test exists to catch: it asserts on the API response, not the rendered page, because the rendered page is not where the guarantee has to hold.

What I would take

C, shown as a gap

Take C. §10's own rule: if it came up at the table it shows up; already settled that a name spoken inside revealed prose is fair to show as a link; hiding the chip (A) fights the sentence it sits inside, which reads as broken rather than careful. Once the link exists, a dead generic 404 (B) costs the same spoiler exposure as a gap page (C) for none of the benefit: same name, same implied existence, but B gives the player nothing back for it and reads as an error. The type badge cost I would accept: "faction" without a name attached to nothing is a small enough leak next to a page that otherwise fills itself in as the campaign continues.

Cheapest way to find out this is wrong: ship it and watch whether players start using gap pages as a checklist ("we haven't cracked the Ledger yet") in a good way or a metagaming way. If a table starts making real decisions off which gap pages exist rather than off what happened in fiction, the type badge is doing more work than intended and needs to go, which is a copy change, not a rebuild.

What this locks in

  • #83 ships the read-only public view as a genuinely separate render (own skin, own templates), not the app shell with a permissions flag, and the gap page from C is one of its states.
  • #85's test asserts on the payload for an undiscovered entity: {name, type} only, no description, no facts, no relations, no images; the gap page is built from that sparse response, not from a full entity object with fields hidden client-side.
  • Locks that a mention chip inside already-revealed prose is always a real link; whether its destination is full or a gap depends only on that entity's own revelation state.
  • Deferred, explicitly and by spec: players writing into the wiki is not v1. Nothing here (a read-only join, a stateless skin) requires a schema change to add it later.
