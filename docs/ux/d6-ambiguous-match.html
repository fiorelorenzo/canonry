Why this is a decision

SPEC 6.4 fixes the mechanics: above a high similarity it is a match, below a low one it is new, and in between the user is asked, one question, never a silent guess. The fixture sits exactly in that band: the incoming article "Il Ratto Dorato" scores 0.86 against the existing entry The Gilded Rat. What the spec leaves open is what the question actually shows and when it interrupts the GM.

The alias list already makes this look obvious to a human: The Gilded Rat is known as "Gilded Rat Tavern", and the incoming note is titled with what would become its third name. That is exactly why the rule matters here rather than feeling like bureaucracy: SPEC 6.4 is explicit that "normalised names and aliases stay in the loop as a cheap pre-filter and as a tie-breaker, never as the decision." A string match this close is precisely the case a false merge hides inside, two different taverns that both happen to translate to something gilded.

Guardrail 3 every proposal shows its evidence, never an arbitrary confidence score. "0.86 similarity" is exactly the sentence this page is not allowed to print anywhere a GM can see it. The question has to be answerable from what the two entries actually say, not from a number the GM has no way to judge.

Options

A

Live, one at a time

The moment the matcher lands in the ambiguous band, the run pauses on that document and asks immediately. The GM answers before the import continues.

Buys

  • Resolved immediately, so the dry run's bucket counts (D3) are already final by the time the plan renders.
  • One decision in full context, nothing to remember from earlier in a long run.
  • Simplest to reason about: the loop genuinely waits, no separate queue to keep in sync.

Costs

  • A GM who is not watching (see D2's "closed the tab" case) leaves the whole import stalled on one question, defeating the point of checking back later.
  • Interrupts a run the GM chose to watch as a progress bar or a live feed, breaking either monitoring style mid-flow.
  • A vault with many near-duplicate notes could pause repeatedly, turning "roughly 9 minutes" into an unpredictable, attention-hungry wait.
B

Collected, answered before the dry run

The run never blocks. Every ambiguous match found along the way is queued silently, and the queue is answered in one batch screen right before the dry run plan is computed, since the plan's bucket counts depend on the answers.

Buys

  • The run itself is never interrupted, so D2's estimate ("about 9 minutes") stays an honest number regardless of how many notes are ambiguous.
  • Three questions answered back to back is a short, self-contained task, easier to commit five minutes to than an unpredictable series of pauses.
  • Sits exactly where it is needed: the dry run cannot show final counts until these are resolved, so the screen order teaches that dependency for free.

Costs

  • A GM who watched the whole run only to hit three more questions at the end may feel like the wait was not actually over.
  • Matching has to run as a distinct pass after extraction rather than inline per document, a real pipeline constraint, not just a screen choice.
  • If a vault has forty ambiguous matches instead of three, "before the dry run" becomes its own review session, needing the same batching care as D4.
C

Live, non-blocking, batched as they accumulate

The run keeps going regardless. A small counter appears wherever the GM is watching (the progress screen from D2), and clicking it opens the same batch of questions, answerable any time during or after the run.

Buys

  • Never blocks the loop like A, never makes the GM wait for the whole run like B; answerable the moment it appears or much later.
  • Fits naturally on top of D2's live-feed or progress-bar screens as one more honest counter, no new screen to navigate to mid-run.
  • A GM who likes answering things immediately still can, just without stalling the other 213 documents while they think.

Costs

  • Three different possible moments to answer (during, right after, or ignored into the dry run) is three states to test and three ways for a GM to lose track.
  • If ignored, it has to resolve somewhere before the dry run can compute final buckets anyway, converging back to B's screen with extra steps taken to get there.
  • The most engineering of the three: a live counter, a background queue, and a hard deadline for when "later" runs out.

Rejected outright

Show the similarity score and let the GM judge the percentage

"86% match, are these the same?" is the most literal way to ask this question and it is exactly what Guardrail 3 forbids: never an arbitrary confidence score. A GM has no way to calibrate what 0.86 means for embeddings they never see trained, and a number invites treating 90% as "probably fine to skip reading," which is the silent guess SPEC 6.4 explicitly rules out. The evidence sentences from both entries are the only thing that should ever justify the answer.

What I would take

B, collected and answered before the dry run

I would take B. The estimate in D2 promises a number of minutes, and A can break that promise on any vault with a few ambiguous notes, which is a worse failure than three extra questions at a predictable, expected moment. C solves the same problem as B with meaningfully more engineering (a live background queue with a soft deadline) for a benefit, answering slightly earlier, that most GMs will not use anyway since they are watching the run finish either way.

Cheapest way to find out this is wrong: ship B, and log how many ambiguous matches a typical vault actually produces. If it stays in the low single digits, as the fixture suggests, B's one short batch screen is right-sized. If some sources routinely produce dozens, batch answering needs D4's own filtering and triage, not just a plain "question 1 of 40".

What this locks in

  • #37 the matcher has to expose which specific pairs sit in the ambiguous band as a distinct, queryable state, not just a final match or no match, since this whole screen depends on that middle state existing and being enumerable before the dry run runs.
  • Matching becomes a defined pass with a clear boundary: extraction can finish while matching questions are still open, and the dry run plan cannot be computed until they close.
  • Hard to undo: once "same place" merges aliases and text into a proposed update rather than creating a duplicate, reversing a wrong answer later means unmerging an alias and a revision, not just deleting a row.
  • Deferred on purpose: what the field conflict screen looks like once two entities are confirmed the same and their text actually disagrees, which is D5; how the resolved match count feeds into "31 new" or "19 to update" in the plan, which is D3.
