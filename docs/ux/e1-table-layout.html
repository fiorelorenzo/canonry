Why this is a decision

SPEC 8 fixes the rule: nothing the GM sees at the table waits on an LLM. And it fixes what the declaration does: "they have entered Valdoria" sets session_context, which pins the place's main characters with a 2-hop graph query, offers contextual quick actions, and starts warming the next ring. It does not fix what table mode is as a surface, or what the declaration gesture looks like. Both are load-bearing: #72 builds the exact declaration widget, #73 builds the exact pinned query, and if either gets decided implicitly by whoever writes the first component, the two are likely to disagree about what a "place" is or how context change propagates to the rest of the screen.

Guardrail 1 propose, never apply. Whatever declares context, the GM says it. Nothing infers it from what was said aloud and switches state on its own. A1 already settled that table mode is dark by default with taller rows; that is inherited below, not re-argued.

Options

A

Separate screen

A dedicated /table route, its own item in the main nav. Leaving it means leaving table mode entirely.

Buys

  • Nothing on screen competes with the table: no sidebar, no entry chrome, maximum room for pins.
  • A route is the simplest thing to build and the simplest thing to bookmark or reload.
  • Unambiguous: the GM always knows whether they are "in" table mode.

Costs

  • Aldric's full entry (his history, his relations) is one navigation away, which means leaving.
  • Nothing about session_context follows the GM if they duck into Entries to check something.
  • A second, parallel place to keep in sync with the rest of the nav as the app grows.
B

A mode the whole app switches into

A toggle in the topbar of any screen. The chrome reskins to dark and tall; a context strip persists across every page while it is on.

Buys

  • The GM can open Aldric's full entry for a name they half-remember without losing the pins.
  • Matches A1's lock: table is a density mode over one app, not a second design system.
  • The strip is a single component every screen already has to render around, forcing discipline.

Costs

  • Every existing screen (Entries, Works, Ask) needs a "table mode is on" variant that fits a strip.
  • Two states per screen doubles what a reviewer has to check before shipping any of them.
  • "Am I still in table mode" is one more thing to track than a route the URL already answers.
C

A layer over the wiki

A dockable drawer, summoned over whatever page is open. The rest of the app never changes skin at all.

Buys

  • Zero disruption to the rest of the app: no second skin, no strip every screen must reserve room for.
  • Cheapest to ship: one floating component, not a mode every existing screen has to support.
  • Works naturally as a "glance and dismiss" pattern that fits a GM checking one card mid-scene.

Costs

  • Narrow by construction: four pins and four actions is already tight in 300px of drawer.
  • Has to be re-summoned on every page load unless it remembers state, which is a feature to build.
  • Splits "the table" from "the wiki" exactly where A1 said not to: a second visual register, not a mode.

Rejected outright

Detect the location from what was said and switch context automatically

Tempting because "they have entered Valdoria" is exactly the kind of sentence a transcript listener could catch. Two failures stack here. It needs a model in the loop to parse speech into a place, which cannot be bounded under the instant lane's 100 ms and turns a graph query into a guess. And it changes session_context (which pins NPCs, warms the next ring and anchors every revelation row created from here on) without the GM doing anything, which is Guardrail 1 applied to state instead of prose: an AI system changing what the product believes is true, unasked.

What I would take

B, a mode the whole app switches into

Take B. A1's own lock-in already commits to this shape: table mode is "not a separate design system, only a separate density mode," which only makes sense if the rest of the app is one click away while it is on. A dedicated screen (A) is the cheaper build and the one I would ship first if the strip variant slipped, but it quietly encourages a second information architecture, and a layer (C) is too small to hold what E3 is about to put in it.

Cheapest way to find out this is wrong: build the persistent strip first and actually run a session against it. Open Aldric Vane's full entry mid-scene, then try to get back. If the instinct is to reach for a "back to table" button that the mode does not have because the mode assumes you never left, the boundary is wrong and table mode needs to be a screen after all.

What this locks in

  • #72 ships the declaration exactly as drawn: an autocomplete over place-typed entities surfaced from a context chip, not a free-text box a model has to parse into an entity id.
  • #73's pinned-card query fires on whatever event B defines: a mode toggle plus a context pick, which is a different trigger shape than a route change (A) and has to debounce against the GM changing their mind mid-type.
  • Locks table mode to the same component library and skin tokens as the rest of the app; a redesign of one is a redesign of both.
  • Deferred on purpose: which actions sit in the quick-action row (E3), how the lanes are shown on each pin (E2), and the one-handed phone shape of this same strip (E4).
