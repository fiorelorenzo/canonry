Why this is a decision

A ten-entry propagation plan reviewed at two clicks each is a minute of work. Two hundred extraction proposals from an import at two clicks each is an evening nobody signs up for, and D4 owns that screen. What D4 does not own, and what has to be settled first so it does not reinvent it badly, is the vocabulary of the click itself: what moving between proposals feels like, what accepting one feels like, and where, if anywhere, a single action is allowed to cover more than one entry.

Guardrail 1 is not negotiable: propose, never apply, per entry, no accept-all default. SPEC §6.4 reads at first glance like an exception: "the GM can accept the whole plan or walk it entity by entity", but the plan it means is the dry-run categorisation itself: 142 unchanged, matched by exact source id, nothing of the GM's at stake, silently applied by the merge engine's own rules (§6.4's merge table). Nothing there writes prose to canon. Every bucket that does: new entities, conflicts, and every propagation diff: still goes through one accept per entry. Confusing the two is the failure mode this page exists to prevent.

Guardrail 1 the agent that edits without asking is the single most hated behaviour in coding copilots, and a campaign's canon has no git diff to fall back on. A bulk action on content the GM has not read is that failure mode wearing a progress bar.

Options

A

Buttons per card

Every proposal sits in a scrollable list, each with its own Accept and Reject.

Buys

  • No modal state to learn: what you see is what you can click.
  • No ambiguity about which row an action hit, even after scrolling.
  • Cheapest to build: it is C3/C4's list with two buttons added.

Costs

  • Fourteen small targets for seven entries; real scrolling near the ~10 cap.
  • Nothing narrows focus to one entry's evidence while deciding it.
  • Does not scale to D4's two hundred without inviting a button that clicks many at once.
B

Keyboard queue

One proposal focused at a time. j/k move, a accepts, r rejects, u undoes. Live, over the seven entries the Aldric Vane edit touches. Click inside, then use the keys.

Buys

  • Reading and deciding happen on one entry, at the size its evidence deserves.
  • j/k/a is the vocabulary a GM who has reviewed a pull request already has.
  • The undo window is cheap here: there is always exactly one last action.

Costs

  • A mouse-only GM gets nothing from the shortcuts and must discover the list still works.
  • Needs an explicit focus state a button-only list does not.
  • A wrong key while distracted risks a fast accidental accept; undo mitigates, it does not prevent.
C

Swipe-style focused review

One proposal fills the frame. Left rejects, right accepts, the next slides in.

Buys

  • Nothing competes with the one proposal on screen while reading its evidence.
  • Maps directly onto E4's phone table mode and its one big touch target.
  • The counter and two buttons are the whole interface, learned in one use.

Costs

  • A full screen per two-line proposal hides the plan's overall shape.
  • Optimises for a fast decision, and fast is the muscle memory that turns into blind accepts.
  • Skipping around ("come back to this one") is awkward with no visible list underneath.

Rejected outright

An "Accept all 7" button behind a confirmation dialog

Guardrail 1 is explicit: no accept-all default, per entry, full stop. A confirmation step does not fix this: it is still one click applying seven unread diffs, and the modal only teaches the GM that clicking through warnings is how this screen works. This is precisely the failure mode SPEC §3 cites from coding copilots: the agent that edits without asking, dressed as a dialog box instead of a silent write.

What I would take

B, with A's buttons always visible on the focused card

Take B: a focused queue, walked with j/k/a/r, is the only option that scales the same way from ten entries to D4's two hundred without changing shape: the queue is what makes bulk tractable, not a bulk button. It should never be keyboard-only: the same Accept and Reject buttons from A sit on the focused card so a mouse-only GM loses nothing, and the small list above it (visible in the mock) is what lets the GM jump around instead of only stepping forward. C's full-screen focus is worth borrowing for E4's phone layout specifically, where a thumb and a lit table make a keyboard moot, but it should not be the desktop default: it hides the plan's shape entirely.

Where the line on bulk sits, stated plainly: the only action that ever applies to more than one entry at once is greenlighting §6.4's non-destructive merge bucket: fields unchanged since the last import, matched by exact source id. Anything that writes new prose, a new relation, or a conflict resolution goes through this queue, one at a time, whether it arrived from a propagation plan or from D4's import review.

What happens to an accepted proposal that turns out wrong: it became a normal revision the moment it was accepted, tagged author_kind: ai_accepted (§4.4, guardrail 2). There is no special undo for AI content because none is needed. Reverting it is opening the entry's history and rolling back, exactly like reverting a human edit. The toast above is a narrower, faster safety net for the fat-finger case, seconds after the click; the revision history is the one that matters days later, and guardrail 1 only buys anything because that history is never optional.

Cheapest way to find out this is wrong: ship B for propagation first, where the cap keeps a plan under ten. If GMs still reach for a bulk action there, the keyboard queue is not the friction they are trying to remove, and D4's two-hundred-entry problem needs a different answer than "the same queue, more of it".

What this locks in

  • #51 ships the per-entry diff surface using this exact interaction: focused card, visible buttons, j/k/a/r, an undo toast, not a placeholder list waiting for a second pass.
  • #42 inherits the same vocabulary at import scale. D4 decides the column layout, batching by type, and how conflicts are grouped; it does not get to invent a second way to accept a proposal.
  • Once j/k/a is trained muscle memory across propagation and import review, changing the bindings later costs more than it looks like. Treat this vocabulary as fixed once #51 ships.
  • Deferred on purpose: a touch/swipe mode for the phone belongs to E4, once that screen's own constraints (one hand, a lit table) are decided.
