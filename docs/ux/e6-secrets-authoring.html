Why this is a decision

§10 fixes the model: World Anvil's, exactly: hidden content inside public entries, GM notes always private. It leaves open how the GM writes the two, and how they check what a player would actually see. Get the authoring form wrong and one of two things happens: either secrets live in a place disconnected from the sentence they attach to, so a GM writing at speed forgets to hide them, or the GM ends up maintaining something that behaves like a second copy of the entry to keep straight in their head, even if the database never literally duplicates it.

Guardrail 6 nothing unreviewed is ever published to players, absolute. Whatever the authoring form, the GM has to be able to see the player's version, not just trust that colour-coding in the editor means the filter will behave the same way in production.

Options

A

Inline block, typed in place

Fenced blocks written exactly where they belong in the flow of the prose; same document, same continuous edit, rendered tinted as the GM types.

Buys

  • True WYSIWYG parity: the GM view and the player view are the same layout, minus some spans.
  • A secret stays exactly where it is contextually relevant, next to the sentence it complicates.
  • One continuous document to write in, no context-switch between "the entry" and "the secrets".

Costs

  • Syntax has to be learned; a stray typo in the fence can leave a block unrendered as raw text.
  • Nothing stops a secret from being typed mid-sentence in a way that reads oddly once removed.
  • Coordinating this syntax with B2's mention syntax is a real dependency, not a free choice.
B

Marked section

Secrets and GM notes live in their own named headings within the same document, always in a predictable place, not interleaved in the prose.

Buys

  • Predictable: "where do I write a secret" always has the same answer, no fence syntax to recall.
  • Skimming the raw document for what is private is trivial; it is always at the bottom.
  • Plays well with an outline or table-of-contents view of a long entry.

Costs

  • A secret about one specific sentence sits paragraphs away from the sentence it complicates.
  • The mock above shows it plainly: the heading itself has to stay or the layout jumps, so "Secrets" sits empty in front of the party, a smaller version of E7's spoiler problem.
  • Every entry accretes two boilerplate headings whether or not it has anything to hide yet.
C

Separate panel

A GM-only pane next to the public one. Secrets are written against the public text, not inside it.

Buys

  • Impossible to leak by a stray keystroke: the public pane physically cannot contain a secret.
  • The GM pane can hold longer prep notes (plot hooks, stat blocks) without cluttering prose.
  • Easiest to explain to a new GM: "left is what they see, right is yours".

Costs

  • Preview is a pane switch, not a filter on one document; the GM never sees the two truly merged.
  • Writing a secret means re-finding which public paragraph it attaches to, across two panes.
  • Closest to a second copy in spirit, even when the storage underneath is a single row.

Rejected outright

Ship the tinted blocks and trust the colour, skip the preview toggle

Cheaper to build: amber for "hidden", red for "GM only", and rely on the GM reading their own markup correctly. It fails because colour-coding is a promise about the editor, not a guarantee about the payload: a stray unclosed fence, a nested block, or a bug in the filter can leak a span the GM never meant to publish, and nothing in the editing surface would show it. Guardrail 6 is absolute, and #85 exists precisely because "the markup says it's hidden" is not the same claim as "the API omits it": a live preview built from the same filter as the real players' wiki is the only way the GM can verify guardrail 6 by looking, rather than by trusting.

What I would take

A for secrets, B's discipline for GM notes

Take A. Inline blocks keep one document and a true WYSIWYG toggle, which is the cheapest way to guarantee the GM view and the player view are actually the same layout with spans removed, not two things that merely agree today. The one thing I would not inline freely: GM notes. A secret is content that will eventually read as prose once revealed, so it belongs exactly where that prose goes; a GM note is meta-commentary that was never going to be prose, and letting it scatter through the document the way a secret does risks one accidentally reading as connected sentence flow. GM notes get B's discipline: a fixed, always-GM-only spot; while secrets stay inline where they are said.

Cheapest way to find out this is wrong: write three real entries with a working GM this way and watch whether they reach for the fence syntax unprompted or keep pasting secrets into a GM-notes field out of habit. If habit wins, the marked-section model (B) is the one that matches how GMs already think about their own notes, and inline is solving a problem they did not have.

What this locks in

  • #84 ships two distinct block kinds, not one: a secret that unlocks on its own revelation, and a GM note that never leaves the editor; which the schema has to represent as
  • #85's test has to assert against the same filter this preview toggle uses; if the preview is a second implementation of "what's hidden", it can drift from the API and pass its own test while the real endpoint still leaks.
  • Locks the inline fence syntax as a dependency on B2's mention syntax; both live in the same editor and cannot each invent their own bracket convention.
  • Deferred: whether a secret can itself contain a mention, and what happens to that mention's chip before the secret's own reveal, belongs to B2 and E7 together, not decided here.
