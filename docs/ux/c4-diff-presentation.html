Why this is a decision

Spec 5.1 step 4 fixes what a diff must contain: the source sentence and the relation it travelled along, and says nothing about its layout. Every reviewable diff tool the team has used borrows from code review, and code review's layout is built for lines that either match or do not. Prose does not diff that cleanly: a rewrite can keep the sentence's shape and change its meaning entirely, or change three words and leave the rest untouched. The layout chosen here is what a GM reads immediately before every one of the roughly ten accept decisions a propagation run asks for, so it has to work for a one-clause change and for a whole paragraph without looking like two different products.

Guardrail 3 every proposal shows its evidence: which entry, which sentence. The diff is the primary place that evidence is read, so the layout is not just presentation, it decides whether the evidence is actually seen before the accept button is pressed.

Options

Fixture: The Valdoria Watch's leadership paragraph still names Aldric Vane captain, plus the field change it implies; Iselde Wrenn's relation to him flips from appointed to dismissed.

A

Unified, sentence-level marks

Reading order. The old sentence, struck, immediately followed by the new one, inserted, inline in the paragraph.

Buys

  • Matches how the GM already reads the entry; no separate mental map for the diff.
  • Old and new sit close enough to compare without scrolling or crossing a column.
  • One grammar for both prose and field changes, shown in the same reading order.

Costs

  • A paragraph with several sentence-level marks gets busy fast, the same risk C1's worst case names.
  • Struck-and-inserted prose reads slower than either state alone; the eye filters twice.
  • Never shows the paragraph as it will actually read once accepted, only a red-and-green hybrid of both states.
B

Side by side

Two full columns, was and now. Each reads on its own, nothing struck through inside either one.

Buys

  • Old and new are each fully readable without filtering strikethrough out of the sentence.
  • Familiar from every code review tool; no new comparison habit to learn.
  • Field diffs and prose diffs both fit the same two-column frame without a special case.

Costs

  • Doubles the width a diff needs, expensive on the narrower two-thirds of an aside3 layout.
  • The eye travels across the gutter to match a changed clause to its counterpart, worse for a two-sentence paragraph than a two-line function.
  • For a one-clause change, most of both columns repeats identical text twice.
C

In place, with a toggle

The entry rendered exactly as it will read once accepted, the change marked, with a toggle to swap in what it replaced.

Buys

  • What is on screen after accepting is what is on screen right now; acceptance never surprises the GM.
  • Costs nothing extra for a one-clause change, the common case: five of the seven candidates here are one relation or one clause.
  • The toggle is opt-in, so the default view is the least busy of the three.

Costs

  • Hides the old wording behind a click; if the toggle is missed, evidence gets judged on the new text alone.
  • A four-sentence rewrite has nothing to anchor "in place" against; the toggle would have to swap the whole block, which is B in disguise.
  • Needs its own affordance for a relation row versus a paragraph, which the other two options get for free from shared chrome.

Same diff, one switch: the layouts compared directly, same content, so nothing about the wording changes when the view does.

Rejected outright

No diff screen at all: accept applies the change, revision history is the record

Removes a screen entirely, which is always tempting under a deadline. It breaks Guardrail 3 directly: accepting without ever seeing a diff means the GM never saw which entry and which sentence justified the change, only a description of the proposal in a list. A revision entry after the fact is an audit trail, not the evidence the guardrail requires before the decision is made.

What I would take

C for the common case, falling back to B past two sentences

Take C as the default. Five of the seven candidates in the fixture propagation are a single relation flip or a single clause, and for that shape C is strictly cheaper to read than A or B while still showing exactly what accepting produces. But C's own cost is real: past roughly two sentences changed in one paragraph, "in place" has nothing coherent to toggle against, and forcing it there is B wearing a worse layout. So the rule is a size threshold, not a universal choice: the semantic diff from C3's plan already carries a sentence count per candidate, and that count decides which layout a given diff gets, automatically, before the GM ever opens it.

Cheapest way to find out this is wrong: run the four-sentence Valdoria Watch rewrite from C1's worst case through both layouts with a real GM and see which one they trust enough to accept without reopening the entry itself to double-check. If B still gets double-checked as often as C did, the threshold is not the fix and the real problem is trust in the diff, not its layout.

What this locks in

  • #51 the per-entry diff is the accept/reject surface; whichever layout ships, accept and reject live on this screen, never on the plan or the inbox list.
  • #48 the field diff (appointed → dismissed) has to be representable as one of the semantic diff's changed facts, not just prose with a label; C's toggle and B's columns both assume that structure exists before rendering starts.
  • Hard to undo: a size threshold between layouts means both C and B's markup have to exist and stay in sync, which is more surface than picking one forever.
  • Deferred on purpose: how the changed span within the diff is highlighted (hue, underline, position) is C1's decision, reused here rather than redecided.
