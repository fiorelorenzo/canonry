Why this is a decision

C2 put proposals in an inbox, a nav place with a count badge. E1 made table mode a mode the whole app switches into: while it is on, the sidebar and its badge are not rendered, the GM sees the strip, the pins and E3's dock instead. So the inbox still exists, but for the whole length of a session it sits behind whichever screen the GM is in, exactly the kind of place SPEC 8's rule was written to keep quiet. That rule is specific: nothing the GM sees at the table waits on an LLM. It says nothing about whether the model is allowed to keep working out of sight, or what happens to a batch of proposals that finishes mid-scene. Issue #80 raises the stakes: quick session notes are meant to become proposals too, so a table mode that never shows the count risks a GM never learning their own note turned into anything.

Guardrail 1 propose, never apply, no accept-all default. Whatever a session does to the inbox while it is open, it may not turn "the GM didn't look" into an accept, and it may not turn "the GM didn't look" into a bulk action either.

Options

A

Suspended for the session

Opening table mode pauses propagation. Whatever the GM edits mid-session queues; every run in the queue starts only once the session ends.

Buys

  • The instant lane never contends with a burst of model calls firing the moment a big propagation lands mid-scene.
  • "Nothing runs while the table is open" is one sentence, trivially true, the simplest possible answer to give a GM who asks what table mode does to the copilot.
  • An inbox opened after a session is never mid-update: every row in it finished before anyone looked.

Costs

  • The real cost: a GM who preps mid-session, ducking into an entry between scenes to fix a name or add a note, gets nothing back until they leave the mode, even though nothing about SPEC 8's rule required the delay. Propagation already runs in the background and was never rendered at the table before this option existed either.
  • A three-hour session becomes three hours of queued edits landing at once, the exact "one button, seven changes" pressure C2's own guardrail-1 callout warns about, deferred rather than avoided.
  • Suspending and resuming a whole subsystem on a mode toggle is more to build, and more ways to get wrong, than simply not showing its output.
B

Keeps running, silent, counted on the way out

Propagation behaves exactly as it does everywhere else in the product. Table mode renders none of it; the count is carried on the strip's own exit control.

Buys

  • Nothing the GM does mid-session behaves differently than it would at a desk: propagation already runs in the background everywhere else, table mode just stays a viewer instead of becoming a governor of it.
  • A GM who edits an entry between two scenes gets exactly the review queue they would have gotten at a desk, only picked up a little later.
  • Nothing new to build beyond one number moved onto the strip: table mode already hides the sidebar badge C2 draws, so "quiet" costs nothing more than not adding a toast.

Costs

  • A count that has been silently true for forty minutes only becomes visible at the exact moment the GM is packing up, tired, and least likely to review it that night.
  • Nothing distinguishes "arrived at minute 4" from "arrived at minute 55" until the queue is opened, so a GM who wants to glance at what changed mid-session out of curiosity, not urgency, has no way to.
  • Relies on the GM actually tapping "Exit table mode" to see the number; closing the laptop or switching apps skips the moment entirely.
C

Present in table mode, a third tier behind the dock

Propagation keeps running as in B, but the count and a link into the inbox sit as a quiet third tier under E3's two-tier dock, reachable without leaving the mode.

Buys

  • A GM who is merely curious mid-session, not urgent, can glance at the count and even open one proposal without leaving table mode at all, closing the exact gap B leaves.
  • Nothing about SPEC 8's rule is touched: the tier links to a queue that already finished computing, reading it is a graph query, the same as the pins, not a wait on a model.
  • Matches C2's inbox exactly, just given a second door into the same rows; nothing about the proposal table's shape changes underneath it.

Costs

  • A third tier is a third thing to fit on a dim screen that already carries pins and a dock E3 deliberately kept to two tiers to protect thumb reach; this reopens that count under another name.
  • Reviewing a proposal properly needs C4's diff and C6's keyboard queue, neither of which fits a strip under the dock, so "open without leaving" is really "read one line of a card," the real review still happens off-table.
  • E3 already turned down four equal-weight actions for exactly this reason: not every session-8 concept earns permanent screen space, and a live proposal count is rarer than any of the four E3 gave equal weight to and rejected.

Rejected outright

Auto-accept whatever is still in the queue the moment a session ends

Framed as "don't make a tired GM review anything," and tempting for exactly that reason. It is the same failure C2 and C6 already named for a different trigger: an accept that happens because a session ended, rather than because a human looked at a diff and chose it, is not an accept, it is an apply with a timer attached. Guardrail 1 propose, never apply, per entry, no accept-all default: "the table broke" is not an entry-by-entry review, however sympathetic the reason.

What I would take

B, with one addition

Take B. It is the only option that does not invent a cost SPEC 8 never asked for: the rule is about what the GM sees, and a background propagation run that is never rendered at the table was never a violation to begin with, table mode existing does not obligate the product to pause it. A pays that invented cost directly, the one this brief asked to be specific about: a GM who ducks into an entry between scenes to fix something gets nothing back until they leave the mode they might stay in for three hours. C's third tier answers a real want, a curious glance mid-session, but at a price E3 already decided not to pay for actions far more common than a mid-session review.

The one addition: put the same badge count C2 already renders in the sidebar nav onto the strip's own "Exit table mode" control, exactly as drawn above. That costs nothing new to build (it is the same query, a different mount point) and it means the GM sees the number the instant they reach for the one button that takes them somewhere the number would matter, without a toast, a pulse, or a tier competing with the dock for their attention.

Cheapest way to find out this is wrong: log whether GMs who exit table mode with proposals waiting open the inbox that same night or let it sit for days. If it consistently sits, "silent until the end" is losing propagation results to a tired GM's short memory, and the fix is C's live glimpse or a short post-session nudge, not a redesign of the inbox itself.

What this locks in

  • #47 the inbox's read path does not change: table mode adds no new proposal state, only a badge count read from the same null-outcome query C2 already defined, mounted somewhere new.
  • #72's strip gains one more small piece of chrome, the count beside "Exit table mode," which its build has to reserve room for even though it was not drawn there originally.
  • #79's ordered event stream is what makes "silent" honest rather than merely absent: arrivals still reach the client in order, without buffering, they are just not rendered while the mode is on, so nothing is lost or reordered by the time the count is read on exit.
  • Hard to undo: once GMs learn nothing interrupts table mode, ever, adding a live toast later, even a well-behaved one, breaks a trust C2 and E1 spent their whole decisions building deliberately.
  • Deferred: whether the end-of-session screen drawn above also carries E5's reveal checklist in the same pass, or a separate one, is not decided here; it belongs to E5's own "confirmed afterwards" surface.
