Why this is a decision

B2 settled the stored form: markdown, decorated live, so bold renders bold while the asterisks stay in the source and export (F4) has a plain serialisation instead of a conversion. Lorenzo amended it on the way through: that stored form is right for someone who already thinks in **bold** and [[brackets]], and wrong for the GM who does not and never will. The amendment says a graphical menu has to exist. It does not say what shape that menu takes, and the shape changes three things B2 never had to answer: whether the menu writes the same characters a keyboard would, how a mention sits next to an ordinary format like bold, and what a hand that never touches [[ or / does instead.

Guardrail 1 a mention is a canon write, proposed and accepted like any other, never auto-created on resolve. B2 already rejected the shortcut where a typed bracket silently writes the relation. A menu button is the same shortcut wearing an icon: press "Mention" and the temptation to skip straight to a written relation is exactly as strong as typing a name and hitting enter. Whatever shape wins below still opens B2's own resolve menu, the one with the new row, not a faster path around it.

Options

All four are drawn over the same in-progress edit: the GM has just typed the Aldric Vane paragraph from the fixture and is reaching for a way to format it without typing markdown by hand. Bold, a mention and a fresh [[ autocomplete all appear in every option, so what differs is genuinely the menu, not the content underneath it.

A

Always-visible toolbar

A row of buttons above the editor, present whether or not anything is selected. Click Bold, the selection wraps in **; click Mention, B2's resolve menu opens at the cursor.

Buys

  • Never asks anyone to know a trigger character exists; every action is a labelled button, visible before it is needed.
  • No reliance on / or [ at all, so it costs nothing extra on the Italian keyboards half the target GMs are typing on.
  • Discoverable the same way B2's own comparison to Google Docs argues for: the toolbar is the manual.

Costs

  • Permanent chrome above every paragraph, competing for the same inch A1's reading-room density already worries about (G2).
  • A GM who never leaves the keyboard still needs a chord for each button, which is G3's table to fill in, not a free result of drawing the row.
  • Heading levels beyond two crowd a single row fast; a dropdown inside the toolbar is one more menu to design.
B

Slash menu at the cursor

Nothing on screen until / is typed at the start of a line; a list opens where the cursor is, filtered as more is typed.

Buys

  • Nothing to look at until it is wanted; the editor stays exactly as clean as option C's markdown-source cost list complains it is not.
  • Matches the muscle memory GMs already bring from Notion and Linear, both named alongside @ in B2's own recommendation.
  • One menu covers headings and lists, which the toolbar's row has no natural room for past two levels.

Costs

  • The trigger itself is a modifier chord on an Italian keyboard: / is Shift+7, not the bare key a US layout gets for free, so "cheap because it's just a keystroke" is not true for the team's own likely first users.
  • A third way to start a mention alongside [[ and @, unless it strictly delegates to one of them as drawn above; a fourth, independent path would be a second relation-creation flow to keep in sync with B2's.
  • Invisible by construction: a GM who does not already know to type / gets no hint the menu exists at all.
C

Selection bubble

Appears only over an existing selection: highlight a word, a small pill of buttons floats above it.

Buys

  • The only shape here that retrofits a mention onto text already written, which neither a toolbar nor a slash menu can do without deleting and retyping it.
  • No trigger character to remember or mistype; it appears from the same click or shift selection every text editor already supports.
  • Nothing on screen at rest, same reading-room cleanliness as the slash menu without needing a keystroke to summon it.

Costs

  • Useless for starting a fresh mention at an empty cursor, which is the common case in B2's own mock; the bubble alone cannot be the only affordance.
  • A floating element above the line it belongs to needs headroom the editor's own padding was not previously reserving.
  • Keyboard selection (shift+arrow) still needs a way into the bubble, which is either a new tab-stop to build or, more simply, just the plain ⌘B chord that makes the bubble redundant for that user.
D

Toolbar plus a slash menu

Both A and B at once: the row stays visible, and / still opens the cursor menu for anyone who prefers it.

Buys

  • Covers a mouse-first GM and a keyboard-first GM without asking either to learn the other's habit first.
  • The toolbar's Mention button and the slash list's Mention row both delegate to the same [[/@ flow, so there is exactly one way the relation actually gets created underneath two doors into it.
  • Nothing here is new engineering beyond A and B added together; the command list is shared, not duplicated logic.

Costs

  • Two visible ways to do the same thing at once, including two Mention entries on screen simultaneously, is one more thing to explain in onboarding (D7) than either alone.
  • Still pays the Italian-keyboard tax on / for the GMs who reach for it, same as option B, just with a second way to avoid it sitting right above.
  • Twice the surface to keep visually consistent if either the row or the list changes later; a missed update shows up as the two doors disagreeing about what is on offer.

What I would take

A, the toolbar, alone for now

Take A. The amendment names the audience exactly: someone who does not want to type markdown. A toolbar answers that with zero reliance on any special character, which matters once / and [[ both turn out to cost a modifier key on the layout this team's own first users are typing on; the slash menu's headline advantage, "it's just one free keystroke," is not true here. B2 already gives a keyboard-native path for anyone who wants one, [[ or @, so the menu's job is specifically to serve the person that path does not reach, and a row of labelled buttons is the plainest way to do that.

Cheapest way to find out this is wrong: ship the toolbar alone and watch for support requests asking how to make a heading without touching the mouse. If that request is common and comes from GMs who otherwise type fast, add the slash menu as option D describes, a second door onto the same command list, rather than building it up front against a need nobody has demonstrated yet.

What this locks in

  • #105 the entry editor now ships the toolbar drawn above as part of its own acceptance criteria, not a follow-on: Bold, Italic, two heading levels, a list, a quote and Mention, each one a real markdown insertion decorated by B2's engine, never a hidden format.
  • The mention item is styled like every other button, never in the violet A1 and C1 reserve for the copilot; only the resolve dropdown it opens carries the new badge, because that is the one moment something AI-touched is actually on screen.
  • Whichever action gets a keyboard chord, the chord is G3's to assign; this page only commits to every toolbar button having one, not to which keys.
  • Deferred on purpose: the exact icon set and whether headings collapse into one dropdown button is visual design, not a product decision this set needs to record.
