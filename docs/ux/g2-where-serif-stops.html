Why this is a decision

A1 put serif in canon prose and entry titles, sans in anything with a control in it, and its own stylesheet says the rest out loud: "exactly where that line falls on dense surfaces, diffs, review queues, import tables, is decision G2." The copilot is nothing but dense surfaces. C4 renders a diff in place, inside the entry's own .prose, so the changed clause is simultaneously canon text and a control surface with a toggle button sitting three inches from it. C6 is a keyboard queue: mostly chrome, cards and buttons, except for the one line per card that quotes the entry's actual words, which is the whole point of guardrail 3. D3 is four bucket cards naming real entities next to counts and accept-all buttons. D4 filters the same queue. F5 is a plain metrics table with no canon text in it at all. Nobody has said which of these gets the comfortable 16.5px serif measure and which gets the tool typeface, and every one of them is being built or reworked by a different round-two page right now.

Guardrail 3 every proposal shows its evidence, never a bare score. Evidence only does its job if it gets read, at review speed, not skimmed past. The wrong boundary here can make the one sentence a GM is actually supposed to weigh the slowest-reading text on the busiest screen, or the fastest-reading text on the one screen where slowing down was the entire point.

Decided

C, serif everywhere, including tables, taken on 2026-08-13

Decided C rather than the A recommended below, so there is no boundary rule to apply and no exception to argue about: serif goes all the way down to F5's number columns, and every surface drawn below, diffs, queues, import buckets, admin tables, keeps the same measure.

Two implementation consequences follow from that and are not optional. Serif figures are proportional by default, so a column of them does not line up: every numeric column, F5's table, D3's counts, F2's meter, needs tabular figures set explicitly rather than inherited. Identifiers, hashes and code keep the mono face regardless of the surface around them. Both are #104's token work, not a per-page override someone reinvents later.

The three options below stay as drawn, because a decision keeps its value only while the alternatives it beat are still legible.

Options

The same three components, drawn under at least two treatments each, so the difference is something to look at rather than something to imagine: C4's in-place diff, C6's queue, and one of D3's bucket cards.

A

Serif wherever canon text appears

Any text that is, quotes, or is about to become part of an entry's own prose stays serif, in the entry, in a diff, even inside a queue card. Sans is reserved for chrome: buttons, badges, counts, labels, table cells.

Buys

  • C4 needs zero override: it already lives inside .prose, so "in place" and serif arrive together for free.
  • A GM reading a proposal's evidence quote sees it in the same face as the sentence it will become, which is the entire idea behind "in place."
  • Only genuine chrome, buttons, badges, nav, kbd hints, ever needs the sans stylesheet at all; the rule reads off the content, not the surface.

Costs

  • The boundary is decided sentence by sentence, not surface by surface: every new component needs a judgment call, is this label a canon fragment or a system description, and D3's own "why" line already sits right on that fence.
  • A queue built for fast triage, C6's whole premise, renders its one piece of real content at prose measure and leading, the slowest-reading pairing in the set, on the screen where speed through ten cards matters most.
  • Mixed serif and sans inside one small card is a smaller-scale version of exactly the "twee" risk A1 already flagged for the reading room as a whole.
B

Serif in the entry, sans wherever a control lives

A DOM boundary, not a judgment call: .entry is serif, everything else is sans, full stop, including a diff that happens to sit inside it, because a diff carries a toggle.

Buys

  • Nobody building a new surface has to ask: the entry is serif, everything else is sans, and that is the whole rule.
  • C6 and D3 already read fine in sans, that is how they were mocked all along in the first-round pages; this option changes nothing about work already done there.
  • Nobody debates F5's number columns in a serif face; a table stays a table by construction, not by exception.

Costs

  • C4's diff sits inside .entry .prose by construction, so "sans wherever a control lives" only wins there by overriding the ambient serif back to sans, undoing inheritance the reading room otherwise gives away for free.
  • The single most consequential sentence in the whole product, the one the GM is deciding whether to accept, reads in the calm serif everywhere else in the entry and switches to the tool typeface at the exact moment it is being judged.
  • A GM who accepts the diff and reloads the entry watches the same sentence jump from sans to serif the instant it becomes canon, a typographic seam none of the other options create.
C

Serif everywhere, including tables

No exception, anywhere, for any reason: the same rule that decided A1 keeps going all the way down to F5's number columns. C4, C6 and D3 follow the identical rule already shown under A and B above; this option's own mock is the surface where the cost actually shows.

Buys

  • Total consistency: "is this canon or chrome" stops being a question anyone building a surface ever has to ask.
  • The whole app reads as one voice, reinforcing "the wiki as a book someone keeps" that A1 built the reading room on.
  • The cheapest rule to write down: one line, no exceptions, nothing to maintain as new surfaces get added.

Costs

  • F5's percentages and counts read worse in most serif faces than in a table built for the job; alignment and scanning both suffer for a screen only staff ever see.
  • C6's keyboard hints and D3's counts read like typos rather than commands when a face without a working monospace-adjacent legibility sits under them.
  • The "quiet tool" register A1 explicitly rejected for the app as a whole reappears by accident on any surface built primarily for scanning, not reading.

Rejected outright

Use the serif/sans boundary itself as a second AI-marking signal

Tempting because it looks like two problems solved at once: render an unaccepted proposal's diff text in sans, everything accepted around it in serif, so the typeface itself says "not yours yet" alongside C1's underline and marker. It breaks Guardrail 2 in practice: C6, D3 and D4 all show unaccepted proposals on surfaces that are sans by every option above, entry, queue and bucket alike, so the same signal would mean nothing on three of the four places a GM meets a proposal and something on the fourth. "Unmistakable" has to mean one consistent signal everywhere unaccepted text appears, which is exactly the job C1 already did; overloading typography to repeat it here only makes a future change to either decision drag the other along.

What I would take

A, serif wherever canon text appears

Take A. In every case actually drawn above it is at least as good as B and strictly cheaper: F5's table is not canon text under A's own rule, so A gets the same sans table B does, for free, while also needing no override for C4's diff, which B cannot say. The only real cost, evidence quotes reading slower inside C6's queue, is bounded and fixable with a width cap or a size step, not an ongoing case-by-case call the way B's .entry boundary turns out to be the moment a diff happens to sit inside one. C is A pushed past the point it earns anything, the F5 table above is the proof.

The rule, in one sentence, for whoever builds the next component without asking: if the text is, quotes, or could become a sentence of an entry's own canon, render it serif wherever it appears; render everything else, controls, counts, labels, table cells, sans, regardless of what surface it happens to sit on.

Cheapest way to find out this is wrong: ship C6's queue with serif evidence quotes first, the riskiest and most triage-speed-sensitive surface drawn here, and time real GMs walking the same seven-entry queue against a sans-evidence variant. If the serif version is measurably slower with no compensating gain in how carefully the evidence gets read, the rule needs a size exception, evidence past some character count drops to sans, rather than being abandoned outright.

What this locks in

  • #104 the shared stylesheet carries the rule once, as the default cascade from .prose and a small .evq-style convention for quoted canon fragments outside the entry, rather than every new component shipping its own typeface decision.
  • #105 B2's editor, and G4's formatting menu built against it, inherit this exact boundary: the body a GM types in is canon prose and stays serif, the toolbar or menu around it is a control and stays sans, with no separate ruling needed.
  • #51 C4 ships using the default .prose inheritance rather than inventing a special typeface for diffs, which is the concrete reason A costs nothing extra there and B does.
  • Hard to undo: once evidence quotes ship serif across C6, D3 and D4, changing to sans later means re-checking every review surface's line height and card height math, serif runs taller at the same font size, a relayout, not a class swap.
  • Deferred on purpose: whether dark mode (G1) changes any of this is not addressed here; the rule is stated per surface, not per palette, and needs a second look once G1 lands if either dark option there ships.
