Why this is a decision

I opened all ten. They are not the same problem in ten places, they are two different problems that both happen to use the tag <select>. LanguageControl.svelte:79 offers four choices the product itself ships, and QuickNoteForm.svelte:51 exists to name any entity a GM has ever written down. A control sized right for the first is wrong for the second, and a control sized right for the second is a popover doing far more work than a four-item choice ever needs. Whoever converts call site six is going to copy whatever call site one did, which is exactly how the wrong control ends up in the wrong place if I don't say, once, which shape belongs where.

Guardrail 1 propose, never apply, one accept per entry, the only exception being a field a re-import writes because the source changed and the user never touched it. LanguageControl.svelte:4–8 already draws exactly that line inside one field: "Auto-detect" hands the entry back to the machine's own detection and re-runs it on the spot, while the other three choices are the only ones that write languageSource: 'human' (:39–40), a confirmation the entry remembers afterward. Whatever renders that field has to keep "the machine is guessing" and "a person decided" exactly as separable as the plain four-item list already makes them; a control that turns a deliberate four-way choice into one more clickable blob loses the one bit of state this guardrail exists to protect.

Options

One figure first, what ships today, both call sites, then three lettered options, each showing the same two fields. Every listbox's own labels below render serif per G2 = C, no boundary rule; file:line citations and entity/relation type tags stay mono, the one carve-out G2 kept for identifiers.

A

One control everywhere: the shadcn-svelte Select

All ten call sites take the same button-plus-listbox, no exceptions, no judgment call about which one a given field deserves.

Buys

  • One implementation, one keyboard model, to build once and maintain once.
  • Both palettes (G1) checked once, not three separate times over three controls.
  • The OS widget stops appearing in the middle of warm paper, on all ten fields at once.

Costs

  • A two-option choice becomes a popover for no reason it can point to.
  • A list of every entity needs typeahead a plain listbox doesn't have, so the worst call site, the one shown above, stays exactly as bad as the native version.
  • A native <select> inside a progressively enhanced form posts without JS; a popover doesn't, so every one of the ten grows a hidden input, real work, not a detail to wave past.
B

Three controls, chosen by what the list is

A segmented control for a state, a Select for a vocabulary the product ships, a Combobox with search for anything drawn from the GM's own, unbounded data.

Buys

  • Each control is sized to its list: no oversized popover for a four-item choice, no undersized listbox for two hundred entities.
  • The rule is stated once, about what the list is, not how long it is, so there's no threshold to argue over call site by call site.
  • The unbounded case, the quick note target and the precedence entry behind it, actually gets solved instead of merely surviving.

Costs

  • Three implementations to restyle and to check across both palettes (G1), not one.
  • A segmented control with long labels wraps badly in a language whose words run longer than English's, shown above with the real Italian strings.
  • The rule needs one sentence in the code review vocabulary or it gets applied by taste, one call site at a time.
C

The palette answers the long lists

Short fixed lists keep a Select. Anything drawn from the GM's own data stops being a field and becomes a button that opens the command palette (#149), scoped to "choose an entry".

Buys

  • The hardest call site costs nothing new: the command palette (#149) already has the search, the keyboard model and the fuzzy matching.
  • One search implementation in the whole product, not two competing ones.
  • Genuinely faster for a GM who types rather than one who scrolls.

Costs

  • A form field that opens a global overlay is a surprising interaction, and it takes focus away from the form it belongs to, shown above covering the entire page for one field.
  • The palette grows a scoped "choose an entry" mode, so #149 gets bigger before this gets smaller.
  • Unusable on a phone (I10): a full-screen overlay to fill one field of five is worse than a plain listbox.

Rejected outright

Styling the native select to look like the reading room

Tempting because it costs almost nothing: a CSS reset, our border and radius on the closed state, warm paper behind it. But the option list itself is drawn by the operating system, not by us, and no stylesheet reaches it. The trigger looks right until the moment someone clicks it, and then the browser's own menu opens in its own font, its own light or dark mode, its own scrollbar. That isn't a smaller version of the current complaint, it is the complaint, restated with better paint on the one part that was never the problem.

Hand-rolling our own listbox from a div and a keydown handler

I9 already settled this once: the hard parts of any of these controls, focus management, typeahead, an escape key that closes exactly one layer and not the whole page, come from bits-ui, and shadcn-svelte's Select, Combobox and radio group sit on top of it. Building our own reopens a decision #155 already flagged as a gap in the layer we picked, not a reason to route around that layer a third time.

What I would take

B, drawing the line by what the list is

Take B. The boundary isn't how long a list is, it's what kind of thing it holds: a state gets a segmented control, a vocabulary the product ships gets a Select, a list of the GM's own data gets a Combobox with search. That's more code than A, three components to restyle and check in both palettes instead of one, and I'd rather say that plainly than pretend it's free. The extra code is exactly where the current pain already is: QuickNoteForm.svelte:51 and settings/+page.svelte:193 are both worse under a plain listbox than under a native select with its OS-level typeahead, and A ships that regression on purpose to save a component.

Cheapest way to find out this is wrong: convert the quick note target first, at a real table with a world of two hundred entries, because that's the call site where a plain listbox and a searchable one differ by an order of magnitude. If the Combobox isn't obviously better there, once it's actually in front of a GM mid-session, A is enough and the third control isn't worth the maintenance.

What this locks in

  • #286 stops meaning "add a Select": the issue has to say which of the ten call sites gets a segmented control, which gets a Select, which gets a Combobox, using the table above, not "replace select" as one line of work.
  • #282 and #155 both close against three components landing together, not one; #155's own gap, no select shipped with the control layer, is now a gap in three shapes, and the epic has to track all three as one wave, not stagger them.
  • Each converted call site keeps working without JS or explicitly stops being progressive, a decision made per form as it converts, not one global ruling this page can make for all ten at once.
  • The three controls arrive with their dark-palette pass (G1) rather than after it, and the reading room's tokens map into shadcn's own names in one block per I9, so nothing here restyles a component a second time on arrival.
