Why this is a decision

SPEC 6.7 is explicit about the mechanics: an estimate before the run covering size, time and cost, a queue with a global concurrency limit, a per-user quota, a checkpoint per document, and a ceiling that stops cleanly with proposals intact and asks whether to continue. It says nothing about what fills the nine minutes on screen. That gap matters because nine minutes staring at a spinner is nine minutes closer to the GM giving up and going back to Obsidian.

Guardrail 1 extends past content: the estimate is a consent screen for spending real money and quota, and it needs the same explicit accept as any proposal, never an auto-start the instant a file lands. Guardrail 3 matters too: whatever counts the GM watches during the run, "trust me, it's working" is not one of them.

Options

A

Progress bar with counts

One number going up, one meter filling. The classic "please wait" screen, minimal and calm.

Buys

  • Cheapest to build and to read at a glance, no per-document rendering.
  • An ETA is an honest, well-understood signal a GM can plan around.
  • Never wrong in a way that embarrasses the product; a bar cannot misrepresent a proposal.

Costs

  • Delivers zero value until the run ends, which fights SPEC 14's time-to-first-value metric directly.
  • Nine minutes of a bar is exactly the wait Obsidian does not impose.
  • Gives no evidence of what is happening, which reads thin next to Guardrail 3.
B

Live feed of proposals

Every accepted extraction appears in a running list the moment it clears validation. The GM can start reviewing before document 214 is even read.

Buys

  • First value can land in under a minute, well inside SPEC 6.6's "minutes, not an hour".
  • Doubles as evidence: the GM sees names they recognise from their own world, which builds trust before the run even finishes.
  • "Review 17 now" turns a wait into work, which is the whole point of not losing to Obsidian.

Costs

  • Reviewing mid-run means the entity list is still growing, so a match made now might be revised by a later document.
  • More surface to build: a streaming list, not a single number, and it has to survive a slow network gracefully.
  • A GM who starts reviewing gets pulled away from watching the run finish, which can make "is it done yet" harder to answer.
C

Log

A scrolling technical trace of the loop itself: checkpoints and tool calls, the same shape a coding agent's terminal output takes.

Buys

  • Nothing hidden: every tool call in SPEC 6.3 is visible as it happens, which is the most literal reading of transparency.
  • Doubles as a debugging surface for support, without a second admin view to build.
  • Cheap to build if the job already emits structured events for checkpointing.

Costs

  • Tool names and JSON fragments mean nothing to a GM; it reads as "for developers" on a product that leads with the copilot for everyone.
  • Fast scrolling text is the least calming of the three during a nine-minute wait, closer to anxiety theatre than progress.
  • Delivers the same zero value before completion as A, dressed as more information.

Whichever style wins, three states come from the job lifecycle in #26, #27 and #30, not from the monitor, and look the same regardless of the option chosen:

Cancel

Stop the import now? 58 proposals already produced stay in your review queue. The remaining 156 documents will not be read.

Ceiling reached

paused

Stopped cleanly at its step ceiling, document 180 of 214. 61 proposals are ready to review now.

Closed the tab, came back

Import running in the background: 197 of 214, about 1 minute left. Nothing was lost, this runs server-side.

Rejected outright

Push past the ceiling automatically to avoid interrupting the GM

It reads as a kindness, finish the job, do not make them click "continue". SPEC 6.7 rules it out by name: a ceiling "stops cleanly... and asks whether to continue." Spending past a budget line without a fresh yes is the same failure mode Guardrail 1 names for content, applied to money and quota instead of prose: the agent that keeps going without asking is the one that gets uninstalled after the first surprising invoice.

What I would take

B, the live feed

I would take B. It is the only option that turns the estimate's nine minutes into progress on the metric that decides the product, time from import to first accepted proposal (SPEC 14, item 2). A is safer to build and never misleads, but it is nine minutes of nothing on a screen competing with a tool that asks for nothing at all. C is honest in the wrong language for the audience.

Cheapest way to find out this is wrong: ship B and watch whether GMs actually click into the feed mid-run, versus waiting for the "done" state before reviewing anything. If nobody reviews early, the streaming feed is solving a problem nobody has at the cost of real complexity, and A with a plain "17 proposals ready" counter underneath the bar gets the same honesty for a tenth of the surface.

What this locks in

  • #26 the job lifecycle has to expose live status as a stream or a cheap poll, not just a final outcome, and cancel has to be a first-class state transition rather than a delete.
  • #30 the estimate card's queue position and quota line are not decoration, every option above commits to showing them before the run starts.
  • #27 resume has to surface the exact checkpoint cursor ("document 180 of 214"), so the ceiling state cannot just say "paused", it has to say where.
  • Hard to undo: once B ships, the review queue and the live feed are the same component wearing two hats; splitting them later means two places that can disagree about what happened during a run.
  • Deferred on purpose: what the review screen looks like once the feed or the bar hands off to it, which is D4; what the plan looks like once the whole run is done, which is D3.
