Why this is a decision

SPEC 14 names "time from import to first accepted proposal" as the second metric that decides whether the product works. SPEC 2 names the real competitor: Obsidian, which asks for nothing on day one. Put together, they set a brutal bar: every minute between signup and the first thing the GM actually accepts is a minute Obsidian is not spending. Whichever option wins has to end in a real accept, not a dashboard with an empty state and a checklist.

Guardrail 1 the first accepted proposal has to be a genuine accept, clicked by the GM, evidence visible, exactly like every later one. A demo that fakes the click to look fast is worse than a slower path that is honest, because the first impression of the product's core loop would be a lie about how the core loop works.

Options

A

Import first

Signup leads straight into D1's dropzone. The first proposal is the GM's own world, which is also what SPEC 14's metric literally measures: import to first accept.

Buys

  • Directly serves SPEC 14's own metric, which is defined as import to first accept, not any accept.
  • The GM's real world from minute one; nothing to throw away or migrate later.
  • Reuses D1 and D2 exactly, no separate onboarding-only screens to maintain.

Costs

  • A GM with nothing exported yet, a brand new campaign with no notes anywhere, hits a dead end unless the fallback is genuinely built, not a token link.
  • Slowest of the three by construction: even a fast vault is a wait measured in minutes, not seconds.
  • A bad detection or a messy vault (D1's generic case) can make the very first proposal a low-quality one.
B

Pre-indexed universe, write one entry

Signup offers a derived universe built on an official corpus already indexed (SPEC 7). The GM writes one thin entry, and Complete mode proposes the rest with evidence from the corpus, seconds later.

Buys

  • Fastest honest path to a real accept: no import job, no queue, no minutes.
  • Works for the exact GM A cannot serve, someone with nothing exported yet, without a fallback screen that feels like a consolation prize.
  • Demonstrates Complete mode and a derived universe's precedence rule (SPEC 4.1) early, which A never shows at all.

Costs

  • Does not touch SPEC 14's own metric definition, which is specifically import to first accept; this path could look fast in a demo and still not move the number that matters.
  • A GM whose world already exists somewhere else has to still do the import afterward, so this can read as a detour rather than a start.
  • Needs a licensed, indexed universe ready at signup (SPEC 7's Fandom licensing constraints), which is infrastructure this decision cannot build by itself.
C

Seeded demo world

Signup drops the GM straight into Valdoria Reach itself, labelled plainly as a demo, pre-populated and ready to edit immediately.

Buys

  • The single fastest path to an accept of the three, no decisions, no waiting, no writing.
  • Shows off propagation, the feature nobody else has, before the GM has invested anything at all.
  • Zero honesty risk about being a demo, the badge says so before the first click.

Costs

  • Does not touch SPEC 14's metric at all, and worse than B on this point: it never even reaches the GM's own universe within the flow.
  • Risks becoming the whole session; a GM who plays with Valdoria Reach for ten minutes has produced nothing toward their own world.
  • The best version of this experience does not need a signup wall at all, which makes it a stronger fit for the public landing page (F6) than for the onboarding of a paying account.

Rejected outright

A pre-accepted "welcome" proposal, shown as already applied

Fake a proposal, mark it accepted by default, and let the GM land on a populated entry with a green "accepted" badge already showing, to skip the wait entirely. It is tempting because it removes every honesty problem above in one move. It also breaks Guardrail 1 at the exact moment the product is trying to earn trust: the very first thing a new GM would learn about Canonry is that "accepted" sometimes means nobody clicked anything. That lesson does not un-teach itself later.

What I would take

A as the default path, with B as the built-in fallback, not a separate decision

I would take A, because it is the only option that actually moves SPEC 14's own metric, and that metric is the one the whole roadmap gets judged against. But A is only honest if the "nothing to import yet" case in its own mock is a real, first-class second path rather than a link, so I would build B at the same time, offered the moment a GM reaches the import screen with no file, not bolted on afterward. C is worth building too, but as the public, no-signup demo on the landing page (F6), where "the GM did not write this" is not a cost at all, it is the whole pitch.

Cheapest way to find out this is wrong: ship A with B's fallback link inert (goes nowhere, just logs a click) for the first cohort. If a meaningful share of signups click "nothing to import yet", build B for real next. If almost nobody clicks it, most GMs really do have something to import, and B can wait behind more urgent work.

What this locks in

  • #108 ships as this exact sequence, signup, source or universe choice, first proposal, first accept, measured end to end as the import-to-first-value clock SPEC 14 requires from day one, not added after launch.
  • #5 the pre-indexed universe epic gains a hard deadline: it is no longer only a feature for derived-universe fans, it is the onboarding fallback for every GM with nothing to import, so its licensing and indexing work (SPEC 7) has to be ready before B can ship, not after.
  • Hard to undo: once the metric is wired to "import to first accept" specifically, a later pivot to counting any first accept (including a demo or a written entry) quietly changes what the number has meant since launch.
  • Deferred on purpose: the demo world's own interaction design belongs to the landing page decision, F6, not here; what the estimate and the run itself look like once the GM commits to importing, which is D1 and D2.
