Why this is a decision

#81 asks table mode to work one-handed, at a lit table, held by a GM who is mid-scene and cannot study the screen. §2 is blunt about why this matters at all: the beachhead already runs generative tools at the table, often from a phone propped against a dice tray. E1 through E3 already decided what table mode is and what sits in it; E4 is the same content forced through 314px of usable width, which is where a layout that looked fine on a laptop quietly stops working. Four pin cards do not become four smaller pin cards, they become a decision about what does not fit.

Guardrail 4 the AI switches off completely and a good wiki remains. On a phone this reads literally: if the model is unreachable or the GM has it off, the pinned rows and quick actions below are graph queries and GM-authored state. None of it depends on Ask working.

Options

A

Bottom tabs

A persistent four-tab bar: Here, Actions, Ask, Queue. Whatever the GM needs is always exactly one known tap away.

Tab target 78×48px Row height 44px min Cut aliases, relation labels, full portraits, per-layer sound sliders

Buys

  • Fixed position, zero scrolling: the reveal tab is always the same thumb reach, every session.
  • The queue badge is visible from any tab, so a finished draft is never silently missed.
  • Familiar pattern: matches how every native app a GM already uses on a phone works.

Costs

  • A quarter of screen width is permanently spent on the tab bar itself, on top of everything else cut.
  • Switching tabs to act on a card in another tab (reveal a place while on Actions) costs a hop.
  • Four tabs is already tight; a fifth destination has nowhere obvious to go.
B

Single scrolling context sheet

No tabs at all. A sticky context header, then everything (pins, actions, queue) stacked in one scroll.

Row height 44px min Sticky header 42px Cut nothing structurally, but 2 of 4 pins live below the fold

Buys

  • No navigation model to learn at all: what you see is what you scroll to, in one continuous document.
  • Zero chrome spent on tabs means more of the screen goes to actual content on first paint.
  • New content (a finished proposal) can just append to the bottom, exactly like it happened.

Costs

  • Iselde Wrenn's card is a scroll away right when the scene turns to the harbour magistrate.
  • "Where was the soundscape control again" has no fixed answer; it moves as content above it changes.
  • A long session (more pins, more proposals) makes the sheet longer, not smarter.
C

Search-first

The screen opens on one big field: ask or find anything. Context and actions sit condensed underneath it.

Search field 44px tall, full width Chip target 30px tall Cut pins beyond the first two, no persistent action dock

Buys

  • One field answers "who is this NPC the players just mentioned" without leaving table mode at all.
  • Scales to a huge universe (214 entries) without a navigation tree, which a tab bar eventually needs.
  • Chips double as quick-action shortcuts, so nothing is purely a search affordance.

Costs

  • Typing on a phone at a table, one-handed, in the dark, is the single worst input this product has.
  • The two most likely NPCs are pinned by rank, but a table of four means someone is always cut.
  • The field's usefulness (search) is exactly what nothing at the table should ever need to wait on.

Rejected outright

Shrink the desktop three-pane layout to fit

The cheapest option on paper: reuse the sidebar, main and aside columns from the wiki mocks (A1) and let them stack or scale down. It is rejected because it is not actually an option. ux.css already hides .side and .aside under 900px, and a phone at 314px usable width cannot fit a three-column reading layout at any font size a GM can read across a table without Guardrail 4 failing by omission: not by turning the AI off, but by shipping a screen nobody can actually use one-handed, which is the same as the feature not existing for the one context it was named for (#81, §2).

What I would take

A, bottom tabs

Take A. E1 already committed table mode to a persistent context strip that survives navigation; bottom tabs are that same idea shaped for a thumb instead of a cursor, and they are the only option where "which tab has the reveal button" has one fixed, memorisable answer under stress. C's search is genuinely better for the rare "who was that again" lookup, so I would keep a search entry point inside the Ask tab rather than promoting it to the whole home screen. B's single sheet is the right shape for a session log read afterwards (E5's after-session review), not for a screen consulted mid-scene in three seconds.

Cheapest way to find out this is wrong: hand someone a phone with option A mid-improvised-scene and ask them to reveal Aldric Vane. If they reach for the tab bar without being told which one, the labels and order are right; if they start scrolling or tapping the context chip instead, the mental model is closer to B or E1's own strip than to tabs, and the phone should inherit that instead of inventing its own.

What this locks in

  • #81 ships this exact tab set (Here, Actions, Ask, Queue) sized to real thumb targets, not a responsive reflow of the desktop nav.
  • Locks the phone's pinned rows to a list, not a card grid: name, role, one line, nothing else, because that is what survives 314px legibly.
  • Locks that the queue badge (from E2, E3) is visible from every tab, so a background draft never goes unnoticed just because the GM is not looking at Queue.
  • Deferred: how Ask's five detail levels (§5) fit a phone screen belongs to C8, not here.
