Why this is a decision

§8 names four actions in one sentence: create an NPC here, create an inn, mark as revealed, a themed soundscape, and stops there. It does not say whether all four earn a permanent spot at the table, where they sit relative to the pinned cards, or what happens the instant one fires. That last part matters most: "create an NPC here" is a create proposal, which means it does not write anything, and it fires while the GM is mid-sentence describing a room. If the button's own feedback looks like success, the GM has no reason to come back and accept it later.

Guardrail 1 propose, never apply, per entry, no accept-all default. A quick action is a shortcut to starting a proposal, never a shortcut past reviewing one; however fast the button feels, the accept step it queues does not get to disappear.

Options

A

Full bar, always visible

All four actions sit in one horizontal dock under the context chip, all the time, equal weight.

Buys

  • Nothing to discover: every named action in §8 is one glance and one tap away, always.
  • Simplest mental model: the dock is the same four buttons every session, every place.
  • Easiest to build and to test: no frequency judgement call baked into the layout.

Costs

  • Four equal-weight buttons for actions used at wildly different rates crowds the rare ones in.
  • On the phone (E4) this row alone is close to the full width of a one-handed screen.
  • "Create an inn" sits exactly as prominent as "mark as revealed", which play frequency does not support.
B

Contextual, per target

No generic toolbar. Each action lives on the card it acts on: reveal and "create an NPC" sit on Valdoria's own pin, not floating above it.

Buys

  • Discoverable exactly where its target is. No toolbar item whose object is ambiguous.
  • Scales naturally: a fifth action just needs a home on the right card, not a wider dock.
  • Nothing competes for space above the pins, which stays clean for the context chip alone.

Costs

  • "Mark as revealed" applies to every card type, so the button repeats on every single one.
  • The GM has to remember which card, not just which button, which is a worse fit under pressure.
  • Harder to scan at a glance: four actions now live in four different visual locations.
C

Two-tier: primary dock, one tap behind "more"

The two most frequent actions sit big and thumb-sized in a primary row. The rest are one tap behind an overflow control.

Buys

  • Primary row stays two buttons wide, which is what actually fits a thumb on E4's phone layout.
  • Matches play frequency: reveals and improvised NPCs happen almost every session, inns rarely.
  • Room to add a fifth action later without the primary row ever growing.

Costs

  • "Create an inn" and the soundscape both cost one extra tap, every time, forever.
  • Frequency is a guess from one campaign's shape; a dungeon-crawl table may found places constantly.
  • An overflow menu is one more piece of chrome to test on a dark screen in a dim room.

What "create an NPC here" actually does, regardless of which dock it lives in: the tap is instant lane, no model involved. The NPC itself drafts in the slow lane, 3–10s, always background, always a proposal.

Rejected outright

Insert the drafted NPC straight into the scene as if it were already canon

The dock's whole appeal is speed, and the fastest possible version drops the accept step: the button names the NPC and the GM just starts using it. Guardrail 1 propose, never apply: a name typed into a proposal and a name spoken across the table are not the same thing until a human accepts one of them, and a model-invented name can silently collide with something already canon. Guardrail 2 follows from the same mistake: an NPC the GM is now playing, that nobody has visually marked as unaccepted AI text, is indistinguishable from one that was always there.

What I would take

C, two-tier

Take C. "Mark as revealed" and "create an NPC here" are the actions a running campaign reaches for almost every session; "create an inn" is closer to session-zero or a big worldbuilding beat. Giving all four equal weight (A) optimises for a session that founds a settlement every ten minutes, which is not the common case, and B's per-card placement solves discoverability at the cost of a GM having to remember where each action lives under pressure, which is the one thing a table screen cannot ask for. C's primary row is also the shape that survives the phone (E4) without redesign.

Cheapest way to find out this is wrong: log which of the four buttons actually get pressed across a handful of real sessions once #74 ships. If "create an inn" turns out to fire as often as "mark as revealed", the primary row picked the wrong two and the fix is a config change, not new UI.

What this locks in

  • #74 ships exactly this: one-click contextual actions linked to session_context, with "create an inn" standing in for the general "create a child location" the issue actually asks for.
  • #80's quick session notes are a related but separate capture path (not one of the four named actions here) and are deferred; whichever dock wins should leave room for a fifth "jot a note" action in its overflow tier rather than assuming the set is closed at four.
  • Locks that every quick action's visible result is a toast plus a queued proposal, never a direct write, which C6's accept flow has to be the only path canon travels through.
  • Deferred: the reveal interaction itself (E5) and the lane markers on the proposal card (E2).
