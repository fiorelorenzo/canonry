Why this is a decision

D3 settled the shape of the dry run: four bucket cards, and the "to update" bucket carries its own scoped control, "Accept all 19", sitting next to the plan-level "Accept plan: 19 updates + 31 new". SPEC 6.4's merge policy never asked for that control. Its table has exactly one row for this bucket: a field unchanged since the last import updates silently, because nothing of the user's is at stake. The next row is the one D3's own mock correctly refuses to give a bulk button to: a field the user edited and the source also changed raises a conflict and is never overwritten. Nobody wrote the sentence that says which of those two rows the 19 actually belong to once they are sitting inside a bucket with a button on it.

So the 19 sit on a fork the spec itself opens. Either they are proposals, AI-authored content waiting on a human, in which case guardrail 1 applies at full strength and a bulk "accept all" on nineteen entries is the exact shortcut the guardrail exists to forbid. Or they are not proposals at all, §6.4 already wrote "silently" on purpose, in which case the button changes nothing whether pressed or ignored, because the write already happens the moment the GM starts the plan above it: it is not a shortcut, it is theatre. A control that looks like a decision but is not one is worse than no control. It teaches the GM that accept buttons are sometimes optional, and that habit does not stay contained to this one bucket, it walks straight into the propagation queue next door.

Guardrail 1 propose, never apply: every AI change goes through an explicit accept, per entry, no accept-all default. The words "per entry" are doing the work in D3's own defence of the plan-level button, "a bounded, freshly-computed plan the GM has already seen counted and can inspect before pressing anything." That defence was written for the plan as a whole. Whether it also covers a second, bucket-scoped accept sitting inside the same plan is exactly what nobody has written down.

Options

A

Informational, no accept

The literal reading of §6.4. The bucket states what changed and nothing else. The plan-level button above it is the only control that ever touches these 19.

Buys

  • Matches §6.4's own word: nothing of the user's is at stake, so nothing asks the GM for a decision they were never actually being asked to make.
  • Removes a button that implies a proposal is waiting when none is, the same "is this real or theatre" confusion the current "Accept all 19" label creates.
  • Zero extra clicks for the common case: a GM who trusts routine resyncs handles the whole re-import with one press on the plan.

Costs

  • AI-extracted prose still lands in canon on nothing more than the plan-level click, which covers many entries at once, and "per entry" in guardrail 1 has to stretch to cover that if this option is right.
  • A GM who wants to catch a bad extraction, the Watch's count landing on the wrong number, has to go looking for the diff; nothing prompts them to.
  • A bucket with no button at all can read as broken rather than deliberate, the same failure E7 named for an unstyled dead link, unless the copy is doing real work.
B

One bulk accept

What D3's mock draws today. The bucket keeps its own "Accept all 19", scoped to exactly the rows shown, sitting beside the plan-level button.

Buys

  • Nothing to design or build, this mock already exists and was already reasoned about once when D3 was decided.
  • Symmetric with the other three buckets: every card in the plan has its own scoped control, easy to explain in one sentence.
  • Lets a GM accept updates and new entities separately, holding off on updates specifically if they want to skim the raw import file first.

Costs

  • The label says "Accept all 19" on a bucket that, per §6.4, was never a proposal, so pressing it or not pressing it changes nothing: the plan-level accept already covers these fields regardless.
  • Teaches the "press accept without reading" habit guardrail 1 exists to prevent, on the one bucket where it happens to be harmless, one screen away from the propagation queue where it is not.
  • Two controls that do the same thing, the bucket button and the plan button, is a second surface to keep in sync and a second thing to explain in the product's own copy.
C

Every field, one accept

Treat the 19 as bona fide proposals. Same review queue as C6 and D4, scaled down: one entity at a time, accept or reject, keyboard-driven.

Buys

  • The least ambiguous reading of guardrail 1's own words, "explicit accept, per entry", nothing left to argue about.
  • Catches exactly the failure that matters, a bad extraction on the Watch's sworn count, because looking at the diff is the only way to press accept.
  • Reuses C6's queue verbatim, so the interaction is not new, only the surface it now appears on.

Costs

  • Nineteen decisions on one re-import is a smaller version of the "evening nobody signs up for" that D4's own reasoning names for two hundred; multiply by however many re-imports a campaign runs over a year.
  • Directly contradicts §6.4's own word, "silently": this treats a case the spec explicitly carved out as not-a-proposal as a proposal.
  • Most of the 19 are exactly the kind of thing nobody disagrees with, a repeated alias, a paragraph someone else reworded; asking for a decision on each trains rubber-stamping, the same failure guardrail 1 is trying to avoid, with extra clicks first.

Rejected outright

The 19 never reach the dry run at all

Write them the moment the source changes, before the GM ever opens an import screen, and the whole question disappears along with the bucket. It is tempting exactly because it is the cheapest of all four shapes to build, and it is the one with no accept surface whatsoever, not even the plan-level "Accept plan" D3 already secured: nothing the GM does gates the write, so it is not "no accept-all default", it is no accept, full stop. Guardrail 1 requires an explicit accept before an AI change reaches canon; §6.4 says these fields update "silently", not "before anyone is told". A dry run that no longer shows what is about to happen is not a smaller version of A, it is a different feature.

What I would take

A, with the diff always shown

Take A. §6.4 already answered this: "update silently" is not a hint about how to draw the button, it is a statement that the 19 are not proposals, so a bucket that offers an accept is answering a question nobody asked, and one that offers nothing is answering it honestly. The plan-level "Accept plan: 19 updates + 31 new" D3 already drew is the one human action that touches them, and D3's own reasoning for why that stays inside guardrail 1, "a bounded, freshly-computed plan the GM has already seen counted and can inspect before pressing anything", already covers this bucket by name. Nothing new is being conceded here, only a button being removed that never did anything.

The diff underneath every row is not optional, though. §6.4's exemption is "nothing of the user's is at stake", not "nothing is at stake". A wrong extraction, the Watch's sworn count landing on 318 because the source document had a typo, is exactly as wrong sitting in canon whether a human agreed to it or not, and a GM who never opens this bucket has no way to notice. Showing the full before and after, not just the one-line "why", is what keeps A honest instead of merely convenient.

Cheapest way to find out this is wrong: log whether GMs ever expand or read the diffs in this bucket during real re-imports, and whether a bad field, a wrong count or a wrong name from a bad extraction, ever survives past the session where it would have mattered. If GMs never look and a wrong field reaches a session unnoticed, that is the signal to promote the field types that broke, not the whole bucket, to C: numbers and names earn their own accept, prose rewordings stay silent.

What this locks in

  • #42 "bulk accept and reject review screen" stops covering the update bucket at all under A: the screen it builds only ever has two audiences, the conflicts queue (never bulk) and the new-entity plan (bulk, already agreed). The update bucket is a change log, not a review screen, a smaller and different component than the issue currently assumes.
  • #36 "source references on every imported entity" is written around one content hash per entity. A's diff, and the "why" column D3 already drew ("population paragraph reworded", "sworn count changed"), both need to know which field changed and what it used to say, not just that the entity as a whole differs. That is a per-field hash or a stored prior value, a bigger commitment than the issue's own body names.
  • #37 the matching benchmark decides how often row one of the merge table is even true. A false merge miscounted as "unchanged" writes straight to canon under A with nobody ever asked, so getting #37's threshold wrong now has a direct line to bad canon, not just a duplicate entity the GM merges by hand.
  • Hard to undo: once GMs learn this bucket never asks for anything, walking it back to C for even one field type later is a behaviour change they will notice every import, not a quiet server-side fix.
  • Defers: whether a dense, field-level list like this stays sans at 13px or earns the serif treatment belongs to G2, decided against real content rather than three fixture rows.

The actual defect underneath all three options is that guardrail 1's own sentence can be read either way, and D3 had to argue its way past that once already rather than being able to point at a definition. The tightened wording:

Proposed rewording, SPEC.md §3, guardrail 1

Replacing "Every AI change goes through an explicit accept, per entry. There is no "accept all" default." with:

"Every AI-authored change to canon content goes through an explicit accept, per entry, with one named exception: a field a re-import writes because the source changed and the user never touched it (§6.4) carries no proposal and needs none, since the merge engine, not a model, made that write, and the plan the GM already started is its only consent. Everything else the model produces, however it is grouped or counted on screen, waits for a human to look at it first, and there is no "accept all" default beyond that one exception."
