Why this is a decision

Today /w/[universe] is one thing wearing two hats. apps/web/src/routes/w/[universe]/+page.svelte:67-137 renders an OverviewStrip, then a TypeFilterRow, then a bare search <form method="GET">, then a flat <ul class="mt-4 flex flex-col divide-y divide-line"> of every entry: a name link, a type badge, an excerpt, a right-aligned "changed 3h ago". +page.server.ts:76 backs it with a loader that takes up to 500 entries with no pagination and hands back per-type counts, totalCount, selectedType, query, stripCollapsed from a cookie, pendingReview, quota {used, total}, currentWork and whatChanged. OverviewStrip.svelte:83-135 turns four of those into four small cells in one row: What changed, Waiting for review, Quota, Current work, collapsible and remembered in a cookie. That whole shape is I7 = C, one page, the browser with a collapsible strip above it, taken on purpose over a separate home.

I opened the deployed preview against Valdoria Reach and it does not read as either thing it is trying to be. It is not a home: the four cells are numbers, not a first destination, and the eye lands on the list underneath them within a second. It is not a browser either: a browser's job is finding one entry among many, and the first thing on the page is four cells that are not that. The compromise reads as neither, which is exactly the risk of building "one page, two modes" and never separately drawing what either mode alone would look like. This question does that drawing, so I can tell whether the compromise was the mistake or the four cells were.

Guardrail 1 propose, never apply, one accept per entry. The "Waiting for review" cell is one of the four numbers on this page, and every option below has to keep it a pointer into the existing proposal inbox, never a second place that can accept or reject something. A home page that grows its own review buttons has quietly built a second surface guardrail 1 already forbids on the first one.

Options

A

Big sections on one page

The strip is gone. In its place, three full-width sections with real headings: Continue, the last changed entries as a row of cards with a cover slot, their type and one line of excerpt; Waiting for you, the pending proposals and any running import, each row a quiet path to review it, never a modal, per C2; The world, one block per type, a small grid capped with a "see all" link. Search moves into the palette.

Buys

  • Reads as a home: first glance value, big and warm, every section a real destination.
  • "Waiting for you" is a genuine pointer, not a number, so the proposal inbox gets found rather than counted.
  • A cover thumbnail gives the world a face for the first time; today's route loads no media at all.

Costs

  • Browsing past the cap needs a list this page does not have, so there end up being two ways to reach the same entries.
  • The loader grows a media query it does not run today, and O2's cover answer has to land before this ships.
  • A world with 4 of a type looks padded here; one with 400 looks truncated the same way, on the same layout.
B

The browser grows up, one page

I7 kept, evolved rather than replaced. A masthead panel (world name, an optional cover band, the four strip numbers as large tabular figures per G2), a sticky filter bar (the type rail with counts on the left, a sort control, the search box), and the flat list becomes a card grid: cover thumbnail, type, excerpt, changed time.

Buys

  • I7 stays intact: one page, one place to browse, no new route, the smallest diff of the three.
  • The grid is honest about being a browser, which the flat list undersold with no thumbnails at all.
  • Filter, sort and search sit together where a GM's eye already goes first.

Costs

  • Still a browser with a hat on: the copilot's whole state is a row of four small numbers, same as today.
  • No pagination the loader does not have; a card grid at 500 entries is a worse version of that problem than a flat list, since each row is now taller.
  • The excerpt is the first thing a narrow card loses, so "one line of excerpt" is a promise this layout cannot always keep.
C

Two surfaces, honestly split

/w/<slug> becomes a world home: masthead with a cover band, the same three big sections A draws, plus a recent activity feed. The browser moves to /w/<slug>/entries, a dense functional table: name, type, relations count, facts count, changed, sortable columns, tabular figures per G2, pagination, and j/k row movement inside it, the same bare-key vocabulary G3 already granted a focused review surface.

Surface 2 · /w/valdoria-reach/entries

Buys

  • Each surface does one job well: the home answers "what's going on", the table answers "find one entry".
  • A table scales to 2,000 entries the way a card grid never will, with the same six columns doing the work regardless of count.
  • The home can carry the copilot's numbers and the quiet inbox pointer without competing with a list for the same pixels.

Costs

  • Amends I7, which means editing DECISIONS.md and the register alongside shipping the route.
  • Two clicks to a list instead of zero: Home, then Entries, for a GM who only ever wants the list.
  • The sidebar's "Entries" item and the world switcher both now have to decide which of the two surfaces they mean.

Rejected outright

A world health or coherence score on the home

"98% coherent" or "3 contradictions resolved" is the single most tempting thing to put at the top of a world home, because it looks like exactly the kind of number a dashboard wants. Guardrail 7 forbids it outright: the product says what does not add up and never certifies that a canon is coherent, and contradiction detection runs at an F1 around 52% besides, so any such number would be confidently wrong close to half the time it disagreed with a GM's own read of their world.

A Loremaster-written summary of the world, generated on load

Opening the home on a paragraph the copilot wrote about the state of the world reads well in a mockup and breaks two guardrails at once in the shipped product: it is AI text nobody accepted, which Guardrail 1 forbids outright, and it spends credits the instant the page loads rather than when a GM asks for something, which is exactly what G11's "confirm every paid action" exists to prevent. A summary the GM asked for and can see the cost of first is a different, smaller feature, and it is not this one.

What I would take

C, because the two jobs really are different

Take C. Every session at this page proves the same thing: I open it wanting either "what happened while I was away" or "find this one entry", never both at once, and I have been reading past four small cells to get to whichever one it actually was. A and B both keep trying to answer both questions on one page; A tilts the page toward the first question and loses the list, B tilts it toward the second and keeps the copilot as four numbers. Only C lets each surface be built for the job it is actually doing, and only C's table has anywhere to grow toward 2,000 entries without the home growing with it.

Cheapest way to find out this is wrong: ship the home first, with today's flat list still sitting under it exactly as it does now, before building the dedicated table at all. Then watch whether I ever click through to the list on purpose. If the home answers everything I actually came for, B was enough all along and the table is a route nobody visits; if I keep reaching past the home for the list, that is the signal to build the real table next.

What this locks in

  • #283 and #282 take the shape of whichever option ships; C's version splits the issue into a home and a table rather than one page.
  • A card or a row with a thumbnail depends on O2's cover answer: media_asset (packages/db/src/schema/media.ts:68-98) has no primary, cover or role column today, so O1 cannot ship any grid with a thumbnail before O2 is decided.
  • The loader needs real pagination the moment any list becomes a table: 500 entries with no pages is already a bug waiting for a real world, and C's table makes that debt due on day one instead of postponing it again.
  • Any "waiting for you" section, in every option, is a pointer into the existing proposal inbox and never a second review surface: C2 already decided the inbox is quiet and never a modal, and guardrail 1 does not get a second exception just because the pointer sits on a prettier page.
